# Отражения: PNG-плитки, SVG и генерация полотна

Актуальная реализация GlassSettings. Исходники находятся в
`OpenGlass/Resources/GlassReflection`, поставляются пакетом OpenGlass Resources;
пользовательский PNG для OpenGlass формируется отдельно в ProgramData.
Встроенный каталог дополнений GlassSettings ищет относительно себя: `OpenGlass\`
в родительской папке каталога GlassSettings.exe (MSI-раскладка —
`ProgramFiles64Folder\GlassPlatform\OpenGlass` рядом с `GlassSettings\`);
реестр для этого корня не читается, отсутствующий каталог даёт пустую коллекцию.

Как GS удерживает OpenGlass на своём изображении (одна таблица решений для
старта, hot-plug и Apply) — раздел
[«Синхронизация с OpenGlass»](#синхронизация-с-openglass-одно-правило-для-старта-hot-plug-и-apply);
термины профиль/рецепт/готовое полотно определены там же.

## Источники и коллекция

| Pivot | Источник | Применение |
|---|---|---|
| Текстуры | `Textured/*.png` | Маленькая RGBA-ячейка замощения; повторяется до размеров виртуального рабочего стола (LinenWeave — крупная ячейка 364×368 из бесшовной текстуры пользователя) |
| Рисунок | `Pattern/*.svg` | Самостоятельная векторная композиция, растеризуется в PNG; здесь же «По умолчанию» |
| Другие | Растровые изображения в корне `GlassReflection` | Применяются как есть, без генератора и диалога обработки |

Прежние растровые Pattern поддерживаются прежним путём, но не получают SVG-настройки.
Каталог Tests не включается в коллекцию. Переключение категории не пишет в DWM;
при загрузке страницы выбирается категория активного исходника. «Настроить»
доступно для выбранной текстуры/SVG, не для стандартного отражения и passthrough.
Имена исходников должны быть уникальны между генерируемыми категориями: итоговое
имя — имя исходника с расширением `.png`, без добавленных размеров.

### Пиксельные текстуры

При масштабе 100% пиксели копируются в нативном размере: нет растяжения маленькой
плитки на весь экран, зеркалирования или выдуманного центрального кропа.
Правый/нижний остаток холста заполняется частичным повтором ячейки. Только явный
масштаб пользователя меняет размер ячейки, с округлением и alpha-aware пересчётом:
при уменьшении — периодическое area-усреднение блока исходника (без алиасинга мелкого
плетения), при увеличении — bilinear. Мягкость рассчитывается с периодическим окружением ячейки; шум
добавляется уже после замощения на **весь** холст.

У каждого узора один источник без суффикса темы. При консолидации сохранён
побитово прежний Dark-источник, поэтому утверждённые альфа и геометрия не изменены.
RGB исходника больше не определяет результат: генератор окрашивает альфа-паттерн
цветом из пикера. Пресеты Dark #000000 и Light #A0A0A0 заменяют прежнее хранение
двух файлов.

Методы построения и проверки плиток (правила):

1. Окно периодичности источника, приоритет: (а) точный трансляционный период по
   autocorrelation — окно равняется целому числу периодов; (б) для штриховой
   графики — начала/срезы до 48 px по минимуму абсолютной разности краевых линий
   (белый канал между мотивами скрывает стык); (в) иначе — типичность перцентиля
   стыка. Внутренний кроп, рвущий продолжительность фич, не применяется.
2. Лечение шва: если стык окна больше 1.6 медианы соседних разностей и его
   перцентиль выше 55 — стык перекатывается в центр, полоса 64 px заменяется копией
   далёкого участка с косинусным пером (анлог Photoshop-хилинга), обратный перекат;
   непрерывность на границе тайла получается по построению; для гладких рельефов,
где клон-хил оставляет размазанную полосу, скачок стыка снимается экспоненциально
затухающей от краёв поправкой (SatinWaves).
3. Альфа: линейное отображение яркости с порогом/gain/инверсией и потолком 225;
   carve отсекает фон; detide убирает крапинки-компоненты ≤2 px; итог — один
   источник альфы, цвет добавляет генератор.
4. Ресемпл периодического сигнала: точное area-усреднение с учётом wrap, футпринт
   целевого пикселя 1/коэффициент масштаба по каждой оси; при нецелом периоде тайл
   удваивается до целого числа периодов. Смена масштаба утверждённой текстуры —
   пересборкой из источника, а не ресемплом готового тайла: двойной ресемпл
   накапливает разрыв стыка на уменьшенных видах.
5. Фаза стыка: перекат тайла подбирается точным пиксельным перцентилем по цепям
   разностей строк/столбцов и их парных/четвёрочных средних (масштабы 100/50/25%).
6. приёмка: перцентили шва на 100/50/25% — лишь индикатор (при бимодальном
   распределении разностей возможны выбросы без визуального артефакта); обязательны
   визуальный осмотр полос ±40 px вокруг шва в замощении и монтажа тайла на
   100/50/25%: квадратов, рамок и срезов мотивов быть не должно. Сторона тайла
   ≤1024 px.
7. Источники с водяным знаком: порог убирает знак над светлым фоном, но не внутри
   тёмных пятен; частичное удаление не применяется — остатки очерчивают надпись
   контрастнее; слабую модуляцию принимают осознанно либо запрашивают чистый
   источник и пересобирают текстуру тем же конвейером.

Подготовка исходных 01/02 (не путать с масштабом пользователя):

`Xy` (режим, непрозрачность), `m/L/l/C/c`, `f/S`, `Bb…BB` (градиент — средний
цвет стопов из `%AI5_BeginGradient`). Координаты из HiResBoundingBox.
LightStreaks: 332 тонких серых полосы (яркость .18–.38 × op), alpha = ярк × op
× 2.5, плюс обводка 2.5 pt с 30 % alpha как замена растровому свечению
(7 растров XI отброшены). 114 КБ, 335 узлов. HexHalftone: 929 чёрных точек
полутона объединены в один path (alpha .5), 81 грань шестиугольников — ярк .32 ×
1.6; 54 градиентных подложки PostScript-части не переносились. 188 КБ, 85 узлов.
GlassBars: 5 капсул (alpha .55 × op) и 7 узких полос (alpha .85 × op), 81 растровый
блик отброшен. 4 КБ, 15 узлов.
TriangleMosaic — AI 288×288 (плитка): 432 треугольника трёх тонов (.02/.07/.12
→ alpha ×4.5), надпись «DARK BACKGROUND» (32 фигуры, ярк .40) и чёрные
треугольники (фон) удалены; плитка масштабирована по высоте и повторена
дважды явными копиями групп (`use` рендерером не поддерживается — контракт
теперь проверяет все Pattern-SVG по allowlist рендерера). 31 КБ, 13 узлов.
DotWaveHalftone (реконструкция полутонового растра) и NebulaDrift удалены по решению пользователя.
WaveInterference, SilkWave, AuroraCurtain, CornerGlow, FoldedVeil: по просьбе пользователя все
непрозрачности (stop/stroke/fill-opacity) умножены на 3 (потолок 0.9).
Геометрия и прозрачность прежних рисунков взяты из утверждённых исходников без изменения. `viewBox` и
`preserveAspectRatio` определяют растеризацию; текущие композиции используют
1920×1080 и `none` для заполнения холста. У градиентов добавленных композиций
геометрия задана явно (`x1/y1/x2/y2`, `cx/cy/r`, `gradientUnits="userSpaceOnUse"`):
без явных параметров часть рендереров подставляет сплошную заливку. Пользовательский масштаб применяется
от центра, при уменьшении остаются прозрачные поля. Мягкость ограничивается
краями холста, не заворачивается на противоположный край.

Рендерер — SVG.NET (`Svg` 3.4.7, System.Drawing, Windows). Профиль ограничен:
контуры, простые фигуры, группы, градиенты, clipPath, заливки и прозрачность.
Запрещены DTD, processing instructions, CSS, скрипты, шрифты/текст, image,
use/href, фильтры и внешние ресурсы. XML resolver отключён; до передачи в
SVG.NET проверяются положительные списки элементов/атрибутов. Ограничения:
256 KiB исходника, 512 элементов, глубина 32. SVG вне Pattern не включаются
в коллекции материалов или атласов. SVG напрямую в OpenGlass не передаётся.

## Диалог обработки

Целевая ширина hosted-диалога следует пропорциям превью: высота предпочтительного
превью × отношение ширины virtual desktop к высоте + 64 DIP на отступы, в пределах
480–1120 DIP. Для одного монитора высота 280 DIP (16:9 → около 562 DIP), для
нескольких — 210 DIP, то есть два рядом дают около 811 DIP вместо 1060. Это только
предпочтительный размер: Viewbox не ограничен этим значением и продолжает расти до
280 DIP, если диалог шире. Ширина не вычисляется из ширины root-окна/монитора, shell
только ограничивает её доступным местом. При live-смене топологии предпочтительная
ширина пересчитывается через `HostedDialogHostContext.UpdateMaxWidth`; жёстким
потолком она не становится. Колонка параметров ограничена 340 DIP, а не
растягивается на всё свободное место. Сверху на всю ширину — пропорциональное превью
desktop (высота до 280 DIP). Под ним master toggle.
Ниже слева группы Pivot **Изображение** и **Шум**, справа группа **Цвет**:
четыре пресетные плашки `AccentRecentColorSwatch` (тот же контрол, что на странице «Цвета»)
(тёмная, светлая, текущий акцент Windows, пользовательский цвет), история цветов и кнопка **Посмотреть цвета**. Галочка отмечает точное совпадение выбранного ARGB
с пресетом или цветом истории; произвольный цвет без совпадений не отмечен.
Кнопка открывает Flyout со стандартным `GlassAlphaColorPicker`: оттенок,
яркость, HEX и альфа. При ширине тела от 960 DIP кнопка скрывается, тот же
экземпляр пикера переносится в правую колонку рядом с вертикальными пресетами.
При сужении возвращается во Flyout. Размеры/шаблон пикера не изменяются. Flyout закрывается
при закрытии родительского диалога; изменения сохраняются только по «Применить».
Общий размер заголовков Pivot 14.
Выбранная группа запоминается только на время жизни процесса, включая отмену
и закрытие крестиком; восстанавливается после Loaded Pivot. Числовые поля
используют `GlassSettingsNumberBoxStyle` и Inline «− / +», как Popup → Анимация.

| Параметр | Диапазон / поведение |
|---|---|
| Масштаб | 25–200%, по умолчанию 100% |
| Цвет / яркость / оттенок | RGB из пикера, по умолчанию #000000; альфа паттерна сохраняется |
| Непрозрачность | Альфа пикера 0–255 переводится в существующий параметр 0–100%; применяется к рисунку вместе с шумом |
| Мягкость краёв | 0–20 px, по умолчанию 0; alpha-aware фильтрация цветов без тёмных ореолов |
| Тип шума | Без шума / Мягкое / Плёночное / Точечное / Блочное / Мелкозернистое |
| Интенсивность шума | 0–100%, по умолчанию 0; сила слоя |
| Плотность зерна | 0–100%, по умолчанию 50; доля активных зёрен, не увеличение их размера |

**Без шума** отключает интенсивность/плотность в UI и исключает их из рендера,
но сохраняет введённые значения. Параметры изображения продолжают применяться.
**Применять обработку** отключает вообще все эффекты, сохраняя их значения:
текстура нативно замощается, SVG растеризуется без дополнительных эффектов.
Плашки **Для тёмной темы** / **Для светлой темы** в группе «Цвет» заменяют
отдельную «По умолчанию»: включают обработку и восстанавливают весь рецепт
(масштаб 100%, мягкость/шум 0, без шума, плотность 50) с цветом
#000000 / #A0A0A0 и альфой 100%. Они доступны и при bypass как действие сброса;
редактирование пикера/вкладок при bypass заблокировано.
**Отмена/крестик** ничего не публикуют; **Применить** передаёт настройки в
существующий serial-конвейер страницы. Recipe/PNG в самом диалоге не публикуются;
по «Применить» отдельно запоминается ограниченная история цветов.

### Превью виртуального рабочего стола и обои

`ReflectionDesktopPreview` получает реальные `DisplayArea.OuterBounds` и сохраняет
взаимное расположение мониторов, отрицательные координаты и пропорции общего
виртуального экрана. Два соседних монитора — два соседних прямоугольника; если
мониторы стоят вертикально/со смещением, показано именно это расположение. Общий
Canvas пропорционально уменьшается Viewbox, а не растягивается в фиксированные
16:9. Рисунок — одно полотно: один bitmap отражения на весь рабочий стол, а не отдельная
повторённая SVG-композиция и не копия на каждый монитор. Вокруг полотна отдельная
рамка с тенью; у каждого монитора — самостоятельная скруглённая рамка с отступом
внутри своей области (подробнее в разделе о компоновке ниже). Топология
фиксируется при открытии диалога, а последующая смена конфигурации перестраивает
его без закрытия.

Шахматка удалена. Используются **существующие** `DesktopEnvironmentWatcher.Current`,
`DesktopWallpaperImageCache.BeginLoad/LoadTask/GetDisplaySourceOrLoad` и
`WallpaperPreviewCrossfade` (500ms). MainWindow владеет инвалидированием кеша;
новый watcher, polling, чтение реестра/файлов обоев и декодер в диалог не добавлены.
Общий COM-адаптер `DesktopWallpaperCom.ReadMonitorWallpapers` и расширение
`DesktopWallpaperImageCache.GetMonitorDisplaySourcesAsync` возвращают bitmap
для каждого монитора, включая разные фотографии. Они используют те же read/decode
helpers и общую инвалидацию; COM-указатели освобождаются. При недоступном COM
используется общий display bitmap; пустой per-monitor путь означает сплошной фон,
а не старую фотографию. Точный Windows Span/Tile/Center fit пока не воспроизводится:
фотография заполняет свой монитор через UniformToFill.

Порядок в каждом прямоугольнике **плоский: обои → стекло → отражение**. Между этими
слоями нет inset, смещения, каскада, отдельных карточек или подписей. Стекло
`FlatGlassPreviewLayer` использует тот же `CompositionWallpaperPipelineBuilder`
и активное Vista/Win7-состояние `CompositionPreviewRegistryStates.BuildRuntimeActive`,
что «Стилизация»: blur → Win7 afterglow → tint → opaque overlay. Это не новый
алгоритм blur/смешивания. Конвертация snapshot в WriteableBitmap также общая.
Коэффициент отображения отражения (0.5 × runtime intensity) вынесен в общий
`RuntimeReflectionOpacity`; в создаваемый PNG этот preview-коэффициент не входит.
Материал/атлас в диалог не добавляются.

После события обоев ожидаются актуальные bitmap/стекло; только после подготовки
стекла начинается синхронный wallpaper crossfade, PNG отражения не перерендеривается.
Смена темы/accent также обновляет factual glass. Подписка снимается при закрытии,
устаревшие async обновления и crossfade очищаются.

Живой рендер использует реальные размеры виртуального экрана, а не 384×216,
поэтому масштаб плитки/зерна соответствует финальному PNG. Рендеры сериализованы
отдельным semaphore с debounce и revision guard: во время изменения пикера
старые запросы не накапливают параллельные большие PNG. На больших конфигурациях
мониторов это дороже маленькой миниатюры. Ничего не публикуется до «Применить».
Миниатюры коллекции по-прежнему имеют ровную подложку #909090 и нативное
повторение текстур 148×92; атласы не изменены.

Шапка спойлера следует [общей политике адаптации](GlassSettings-adaptive-layout.md):
«Настроить» слева от слайдера, трек 120–200 px. После переноса таблицы под
заголовок остаётся единый бюджет ширины. При недостатке места для суммы минимумов
`StackFixedActionBelowSlider` переносит кнопку ниже слайдера на третью строку;
возврат идёт в обратном порядке с гистерезисом 1 px. Пороги измеряются общей
таблицей, страница не содержит собственного resize-конвейера.

### Типы шума

Шум — независимый ахроматический слой по всему холсту, включая прозрачные пиксели.
Он не наследует цвет рисунка. Поле g ∈ [−1, 1] задаёт яркость 127.5×(1+g),
а альфа — |g|×интенсивность/100×0.35×коэффициент типа. Почти нейтральные зёрна
прозрачны, а не образуют равномерную серую заливку. Композиция source-over
в straight BGRA предшествует общей непрозрачности. Рендер детерминирован.

| Сохранённый ID | Тип | Характер |
|---|---|---|
| −1 | Без шума | Пропуск шума независимо от интенсивности и плотности; значение по умолчанию |
| 0 | Мягкое | Плавная интерполяция равномерного поля, характерный шаг 2 px |
| 1 | Плёночное | Смесь масштабов 2/1 px, гауссовы отсчёты Box–Muller, ограничение ±2.5σ |
| 2 | Точечное | Отдельные смещённые круглые зёрна в сетке 3 px; покрытие 2×2 субпикселя |
| 3 | Блочное | Намеренные квадратные фракции 2×2 px |
| 4 | Мелкозернистое | Независимые пиксели шести яркостей, без интерполяции; ранее «Наждачный» |

Типы оставлены раздельными: общая интерполяция мягкого/плёночного не означает
одинаковое распределение или спектр. Плёночный тип — стилизация, не физическая
модель фотоплёнки. Плотность выбирает кандидатов зёрен отдельным hash; процент
покрытия зависит от формы и перекрытий и не обязан равняться параметру.

Сила пяти типов согласуется по sqrt(mean(g^4)) на поле 96×96 при полной
плотности, что учитывает совместное влияние яркости и альфы. Более сильные
типы ослабляются до самого слабого, не усиливаются и не клипуются. Это не
обещание одинакового восприятия на любом фоне или при любой плотности.

Мелкозернистое основано на анализе пользовательского NoiseAsset_256x256_PNG.png:
яркости 0/51/102/153/204/255 с количествами 1311/9094/22034/22214/9351/1532.
Средняя 128.30, σ=52.83, горизонтальная корреляция ≈−0.018. Генерируется новое
поле с этим распределением, а не плитка из загруженного файла. Это не обещание
совпадения с материалом OpenGlass, у которого другой контекст композиции.

## Генерация, публикация и профили дисплеев

Общий versioned runtime ABI находится в `GlassShared/include/ReflectionProfileApi.h`,
реализация — **GlassSettings.Native**, а не GlassCompat или отдельная обязательная DLL.
GS вызывает Capture через P/Invoke. Native перечисляет полные прямоугольники через
EnumDisplayMonitors в PMv2-контексте, читает индивидуальные DPI, сортирует геометрию
и хеширует координаты относительно общего origin. Физические ID не участвуют;
изменение основного дисплея без изменения взаимного расположения не меняет ключ.
Снимок ограничен 32 мониторами. Ключ: `<width>x<height>_DPI<first>_<topology hash>`;
для mixed-DPI полный набор DPI входит в хеш, первый DPI не считается общим DPI.

1. `PrepareAsync` сериализует генерации SemaphoreSlim. Размер берётся из общего
   Native-снимка; стороны ≤16384, площадь ≤33554432 пикселей.
2. Проверяется SHA256 источника до/после рендера. Если текущий профиль содержит
   тот же источник/хеш/рецепт/размеры и проверенный PNG, он переиспользуется.
3. Промежуточные файлы — только уникальная папка `%TEMP%\GlassPlatform-Reflection-*`,
   удаляемая в finally. Итог — `%PROGRAMDATA%\OpenGlass\Presets\Textured\<profile>.png`.
   **Один PNG на профиль**, общий каталог и чужие профили не очищаются.
4. Под mutex `Local\GlassPlatform.ReflectionProfiles` повторно проверяется топология,
   сбрасывается Ready текущего профиля, PNG заменяется через временный файл/rename,
   сохраняется State и только последним устанавливается Ready=1. Ошибка не объявляет
   профиль готовым. Предыдущие профили остаются на месте; rollback рецепта не заявляется.
5. Явный Apply записывает DWM через page operation pipeline под тем же mutex и
   проверяет соответствие опубликованного PNG текущему профилю ещё раз.

HKCU `Software\StanislavKa\GlassPlatform\GlassSettings\Textured\Profiles\<profile>`:
`State` (JSON, Version=2, Ready, Source, Output, Width, Height, SourceHash,
OutputHash, Settings, Profile), `Ready` DWORD, `Output`, `OutputHash` REG_SZ.
Settings включает ScalePercent, OpacityPercent, Softness, NoisePercent, NoiseType,
NoiseDensity, Enabled, ColorRgb. NoiseSize игнорируется и нормализуется в 1.
Готовность, ключ, размеры и SHA256 проверяются при чтении; старые глобальные
записи не мигрируются. Повреждённый/отсутствующий профиль даёт стандартные настройки.

### Автоматическое переключение без запущенного GS

Только host-процесс GlassCompat **родной архитектуры ОС** опционально загружает
`<собственный каталог>\GlassSettings\GlassSettings.Native.dll`: абсолютный путь,
restricted DLL search, запрет reparse points, проверка пути загруженного модуля,
V1 exports и версии снимка. WOW64-host и injected-инстансы не исполняют переключение.
Отсутствующая, несовместимая или незагружаемая Native — нормальный soft-skip:
установка платформы без GS поддерживается, зависимость/политика установщика не меняется.

Startup всегда планирует reconcile, в том числе при уже работающем OG.
Существующее top-level host-окно принимает display/DPI/device/settings сообщения
(включая синхронно доставленные), Native debounce 750ms исполняется очередным
host tick (существующий wait до 2s). Host не создаёт registry watcher.
Правило одно и то же у хелпера и у GS: см.
[«Синхронизация с OpenGlass»](#синхронизация-с-openglass-одно-правило-для-старта-hot-plug-и-apply).
Готовое полотно текущего профиля применяется после проверки пути, Ready,
PNG signature/IHDR/размеров и SHA256; если полотна для текущей конфигурации нет,
а применено наше значение, хелпер снимает его, и OpenGlass использует системное
отражение. Чужое изображение (путь вне `ProgramData\OpenGlass\Presets\Textured`)
не перезаписывается и не удаляется. Rендер живёт в GS: `Regenerate` хелпер не
выполняет, он только снимает наше устаревшее значение. Явный выбор default в GS
снимает управление.
Перед записью Native повторяет Capture. Обновление — адресный WM_THEMECHANGED
окну класса Dwm, без рестарта OG и без colorization/broadcast волны.

GS использует существующий DesktopEnvironmentWatcher для display-сигналов.
Открытый диалог Configure при смене ключа **не закрывается**: превью пересоздаётся
на месте, значения редакторов остаются черновиком и не применяются; следующее
открытие заново строит layout и читает рецепт нового профиля (подробнее —
[«Новый профиль при открытой галерее GS»](#новый-профиль-при-открытой-галерее-gs)).
Дополнительные проверки ключа при Primary, генерации и Apply перекрывают гонки.
Внизу справа в preview — менее заметный badge разрешения и набора DPI.

## Права доступа и безопасность ProgramData

GlassSettings **не повышает права автоматически и не изменяет ACL**. Сам путь
ProgramData не гарантирует возможность обычной записи в существующий каталог.
Для выполнения генерации учётной записи процесса требуются:

- чтение исходных ресурсов и право записи/удаления в пользовательский TEMP;
- создание/запись State в указанном разделе **собственного HKCU**;
- traverse/read на родительских каталогах ProgramData/OpenGlass/Presets;
- если Textured ещё нет — право создать подкаталог в Presets;
- для существующего Textured — чтение, создание/запись и атомарная замена файла
  своего профиля (Modify); права удаления остальных профилей не используются.
- процессам OpenGlass/DWM, читающим результат, — Read и traverse к финальному PNG.

Полный доступ/смена владельца/DACL для обычного рендера не нужны. Не следует
выдавать запись на весь ProgramData, бинарники OpenGlass, каталог пакетов Setup
или всю коллекцию исходников. ACL, если они требуются для обычных пользователей,
должны быть ограничены выделенной генерируемой папкой и управляться установкой/
администратором. В текущем OpenGlass Resources MSI явной настройки ACL для
`Presets\Textured` нет: **нельзя утверждать, что Modify уже выдан установщиком**.
Унаследованные права конкретной установки следует проверять отдельно. Запуск
из Build этих требований не отменяет. При AccessDenied применяется обычная
ошибка генерации; обхода в LocalAppData и скрытого UAC-запуска нет.

ProgramData общий для пользователей, HKCU индивидуален. Один пользователь может
заменить последний PNG другого; проверка хеша выявляет несоответствие, но не
создаёт изоляцию пользователей. SemaphoreSlim защищает только этот процесс:
межпроцессная/межпользовательская блокировка не реализована. Новый PNG заменяет
предыдущий и для других DWM-партиций. Откат DWM-снимка не возвращает старое полотно.
При смене конфигурации мониторов при открытой странице полотно строится автоматически
по последнему применённому рецепту; при закрытой странице GS ничего не строит — он
только приводит значение по общей таблице (см. «Синхронизация с OpenGlass»), а
недостающее полотно строится по кнопке «Сгенерировать полотно».

### Диагностика открытия диалога (Debug)

В Output Visual Studio этапы открытия помечаются `[ReflectionConfigure]`:
click → settings → picker → desktop snapshot/cards → render → hosted dialog,
а после Loaded — загрузка wallpaper sources. Обработчик
кнопки выводит полное managed exception и повторно бросает его для штатной
диагностики (ошибка не маскируется под Cancel). Native FailFast этими catch
не перехватывается: для него необходимы код исключения/стек отладчика или дамп.

Полученный журнал GlassSettings.txt до нажатия «Настроить» на Debug x64 с
ed2a5ac содержит успешную генерацию/декодирование AtlasPreview, но не содержит
исключения или следа открытия reflection dialog. Он не устанавливает причину
повторного падения; предыдущий стек про WinRT IEnumerable к нему автоматически
не относится.

Повторный Debug-лог после 0950093 подтверждает завершение monitor snapshot
(count=1, 1920×1080), создания диалога и Loaded composition clip. Последняя
запись — `wallpaper: read monitor sources`; возврат per-monitor источников не
подтверждён. В COM-адаптер добавлены маркеры каждого вызова и освобождения
ресурсов, в общем кеше — маркеры ожидания bitmap. Конкретный упавший вызов
пока не установлен; эти изменения диагностические, не исправление причины.

Следующий пользовательский лог с d356aa7 подтверждает все COM-вызовы,
освобождение указателей и RCW (`wallpaper COM: complete`). Последняя запись —
`wallpaper cache: await monitor bitmap`, без `monitor bitmap ready`.
Это локализует незавершённую async-операцию, но не доказывает место падения:
в это время также может выполняться отложенный render/decode отражения.
Добавлены отдельные Debug-маркеры read/decode wallpaper и render/decode reflection.

После включения first-chance диагностики пользователь поймал
ArgumentOutOfRangeException непосредственно в DisplayArea.FindAll. Этот API
удалён из ReflectionDesktopPreview: геометрия теперь читается через Win32
EnumDisplayMonitors (полные прямоугольники, включая отрицательные координаты),
дальнейшая раскладка использует managed-массив. Это устраняет данный WinRT-путь,
но тождество first-chance исключения и прежнего завершения процесса ещё не
подтверждено; необходима повторная проверка диалога в Windows.

### Разбор Stowed Exception и исправление клипа

WinDbg для пользовательского дампа показал `STOWED_EXCEPTION_80004002` /
`E_NOINTERFACE` в `Microsoft.UI.Xaml!HWCompTreeNodeWinRT::UpdateVisualClipAndTransform`
(WinUI 3.2.1.0), затем FailFast `0xC000027B` при отправке кадра compositor.
Это не стек чтения wallpaper. Из preview удалено прямое назначение
`CompositionGeometricClip` через `GetElementVisual(layers).Clip`: оно конфликтует
с обработкой clip у XAML-owned visual. Обрезка полного desktop canvas по монитору
остаётся штатной XAML `RectangleGeometry`; рамка Border сохраняет CornerRadius
и тень. Отдельная rounded composition-маска содержимого больше не создаётся.
Исправление требует пользовательской runtime-проверки; дамп локализовал render
clip, но локальное воспроизведение на Windows здесь не выполнялось.

После пользовательского подтверждения открытия диалога удалена отдельная кнопка
сброса, редакторы перенесены под полноширинное preview. Для предотвращения муара
готовое полотно полного virtual desktop предварительно уменьшается WIC Fant
до физического размера preview (ActualWidth/Height × RasterizationScale), а не
передаётся напрямую GPU для сильного уменьшения мелких повторяющихся ячеек.
При изменении размера preview миниатюра пересчитывается через прежний debounce
и semaphore. ProgramData PNG остаётся полноразмерным; downsample только для UI.

Редакторы под превью выровнены по верхнему краю (Pivot больше не центрируется

Другие потребители пикера остаются без изменений. Геометрия мониторов сохранена.

Исправлены отсутствовавшие подключения Click у обеих кнопок пресетов.
Проверка теперь требует именно подписки darkPreset/lightPreset, а не только
наличия функции ApplyPreset. Runtime-оценка компактной компоновки — в Windows.

### Текущий масштаб превью и загрузка

По уточнению пользователя PNG-текстуры в preview замощаются при выбранном
ScalePercent в пикселях миниатюры, без уменьшения ячейки вместе с монитором.
Их RenderConfiguredAsync получает размеры отображаемого preview с учётом DPI.
SVG рендерится на полный virtual desktop и уменьшается до preview через WIC
Fant. Финальный публикуемый PNG в обоих случаях остаётся полноразмерным.

До завершения первой подготовки wallpaper/glass и reflection desktop view
невидим (место зарезервировано), отображается ProgressRing. Это исключает
показ промежуточного чёрного слоя. При ошибке отражения показывается ошибка
и доступная подложка, а не бесконечный индикатор. При последующих изменениях
сохраняется предыдущий кадр. Эксперимент UseCompactLayout/ResizeSpectrum удалён.

### Акцент, история и ярлычок

Акцентный пресет использует WindowsPersonalizationService.ReadUserAccentColor
(тот же источник, что «Цвета»), обновляется на ThemeChanged/AccentChanged общего
DesktopEnvironmentWatcher. Плашка обновляется без незапрошенной замены выбранного
цвета отражения; подписка снимается при закрытии.

Четвёртая плашка хранит последний пользовательский ARGB из пикера. До выбора
пользовательского цвета она неактивна. Выбор встроенного пресета не затирает её.
При выборе другого пользовательского цвета предыдущий custom переходит в историю,
а новый занимает четвёртую плашку. Выбор цвета из истории аналогично поднимает
его в custom. Галочка учитывает альфу.

История содержит до восьми уникальных выбранных здесь ARGB; цвета всех текущих
пресетных плашек из неё исключаются (в том числе custom и live-акцент). При
изменении акцента фильтр обновляется. Импорта Windows recent accent colors нет.
По «Применить» история перезаписывается целиком (`RecentColors`, REG_MULTI_SZ),
custom хранится отдельно (`CustomColor`, DWORD) в существующем HKCU Textured.
Изменения до «Применить» локальны; отмена не записывает историю или custom.
Системный акцент и его история не изменяются.

Имя источника живёт в отдельной строке над полотном (слева), а общее разрешение с
набором DPI — в строке под ним (справа, приглушённо). Внутрь прямоугольников
мониторов подписи не попадают. Имя проявляется вместе с подготовленным превью
через изменение прозрачности, поэтому раскладка не прыгает по высоте.

### Узкая компоновка

При ширине тела <620 DIP плашки пресетов располагаются вертикально, история
тоже перестраивается в одну колонку. Ширина панели цвета 164 DIP, параметрам
выделяется оставшийся бюджет без принудительного минимума 260 DIP. При <480 DIP
панель цвета переходит во вторую строку под параметрами. При >=960 DIP остаётся
стандартный inline-пикер; на меньшей ширине — Flyout. Подпись «Недавно
использованные цвета» удалена; сами плашки истории сохраняются.

### Четвёртая плашка как кнопка пикера

Отдельная «Посмотреть цвета» удалена. Четвёртая плашка всегда доступна и
открывает стандартный Flyout по клику; если пикер уже inline — переводит на
него фокус. Пикер получает цвет этой плашки. Начальное значение: сохранённый
custom, иначе первый цвет собственной истории, иначе текущий default пикера;
текущий нестандартный цвет рецепта имеет приоритет. Цвета встроенных пресетов
не сбрасывают custom в пустое/неактивное состояние.

Плашки выровнены слева; вертикальная панель занимает 56 DIP, горизонтальная
216 DIP. Подпись мягкости сокращена до «Размытие, px» / «Blur, px», диапазон
0–20 сохранён в NumberBox и нормализации. Это заменяет прежнюю длинную подпись
с диапазоном, переносившуюся на две строки.

### Распределение доступной ширины редакторов

Пресеты теперь Grid с 1/2/4 колонками (ячейки 48 DIP, промежутки 8 DIP), а не
StackPanel с переключением ориентации. История использует такое же число колонок.
Колонка параметров — star, с MaxWidth 420 DIP: она использует свободное место,
а панель цвета выравнивается справа. Для расчёта сетки резервируется 320 DIP
параметрам и 16 DIP между колонками. Inline-пикер включается только если
помещается его измеренная стандартная DesiredSize.Width (минимум бюджета 300 DIP)
вместе с параметрами, одной колонкой плашек и промежутками. После выделения
места пикеру остаток определяет число колонок плашек. При ширине <380 DIP цвет
переносится под параметры. Прежние фиксированные пороги inline 960 DIP и
вертикали 620 DIP больше не применяются. Размер превью и правила его рендера
не изменены. Runtime-оценка переходов требуется на Windows.

### Итоговая палитра: пресеты, четыре недавних цвета, кнопка пикера

Цветная custom-плашка заменена обычной theme-aware кнопкой 48×48 с FontIcon
Color (E790) и tooltip «Выбрать пользовательский цвет». Она не окрашивается
текущим цветом и не получает галочку. Кнопка всегда последняя в общей сетке:
три встроенных пресета → 0–4 недавних пользовательских цвета → кнопка пикера.
Таким образом, максимум восемь плиток; фиксированной «четвёртой позиции» больше нет.

Текущий пользовательский цвет теперь входит в историю и отмечается там галочкой;
исключаются только цвета трёх встроенных пресетов. Выбор нового цвета перемещает
его в начало истории, сохраняется максимум четыре уникальных ARGB. CustomColor
остаётся памятью начального цвета пикера, а не отдельной цветной кнопкой.
Одна сетка раскладывает все плитки в 1/2/4 колонки без разрыва между пресетами,
историей и кнопкой. Во время редактирования Flyout его кнопка не удаляется из
visual tree: обновляются только плашки истории, вставляемые перед последней кнопкой.

### История только после явного «Применить»

ColorChanged пикера и выбор существующей плашки меняют только pending color,
галочки и preview. Во время жестов история не пополняется и не перестраивается.
Только ветка HostedDialogResult.Primary добавляет итоговый нестандартный ARGB
в начало списка, убирает дубликаты/встроенные пресеты, ограничивает список четырьмя
цветами и сохраняет его. Все промежуточные положения ползунков отбрасываются.
Отмена/крестик не записывают pending color или историю.

### Живое обновление стекла из общего session-конвейера

ReflectionDesktopPreview подписан на SettingsSession.Current.DirtyChanged,
которое используется страницами настроек и вызывается после external-sync
существующего RegistrySnapshotWatchService (HKCU/HKLM DWM). Новых registry
watcher/timer-polling нет. После debounce 150ms и проверки PreviewState обновляются
только FlatGlassPreviewLayer, через прежний CompositionWallpaperPipelineBuilder.
Очередь стекла сериализована, устаревшие запросы отсекаются revision/dispose.
Пути обоев переиспользуются из последнего общего wallpaper refresh, без нового
COM-чтения для каждого DWM-сигнала. Intensity отражения перечитывается без
перегенерации его bitmap. Цвет пикера, история и recipe не меняются. Подписка
снимается при Dispose. Внешние записи видны после штатного debounce/settle
общего session watcher, а не синхронно с каждой записью реестра.

Layout строится из общего Native-снимка при открытии. При hot-plug/DPI-смене
открытый редактор не закрывается: превью пересоздаётся на месте, значения
редакторов и цвет сохраняются как черновик, применяется только явный Apply.

### Диагностика hot-plug (лог пользователя 2026-11-25)

Полученный фрагмент LogViewer: 1048 строк, 10:54:28.921–10:54:49.988,
только PID 9732 (Explorer по описанию пользователя). В 10:54:41.196 и .904 —
TaskbarCompat InvalidateSystemBrushSamples, в .237 и .944 —
ReloadSettingsAndReapply; это не подтверждение перечитывания reflection в DWM.
Записей выбора reflection-профиля/PNG в этом фрагменте нет. Причина наблюдаемого
укрупнения текстуры этим логом **не установлена**; исходный лог после анализа удалён.

В Debug-сборке добавлены подсистемы `GlassCompat / ReflectionProfiles` (optional
loader, startup, входные сообщения) и `GlassSettings / ReflectionProfiles`
(Native reconcile, ключ/размер canvas, ownership, default/cached selection,
результат отправки WM_THEMECHANGED и ошибки). Обе выполняются в native-arch
**host rundll32**, даже если модуль записи — GlassSettings. В LogViewer нужно
захватывать host, а не только Explorer, с момента запуска host до подключения
монитора и ещё несколько секунд после него. Отсутствующая Native по-прежнему
soft-skip, новые сообщения ничего не генерируют и не меняют масштаб.

Повторный лог `LogViewer-2` (126 строк): есть GlassCompat/WinEventDiag от PID 2304
с `mod=Rundll32.exe`, следовательно сообщения из host доходят до LogViewer.
Это callback-поток, а не доказательство выполнения профилей в основном host loop.
Startup host и ReflectionProfiles в фрагмент не попали. Только модульный фильтр
GlassCompat также скрывает Native-решения, помеченные модулем GlassSettings.
Исходный лог удалён после анализа.

Обнаружено различие layout: Native.vcxproj выводит DLL в корень Build/arch/config,
а optional loader поддерживал только MSI-подкаталог GlassSettings. В Debug
добавлен абсолютный sibling `GlassSettings.Native.dll`, **только если** файл
установленной раскладки отсутствует (FILE_NOT_FOUND/PATH_NOT_FOUND). Все проверки
reparse/path/exports/ABI и restricted search сохранены; при ошибке загрузки,
небезопасном или несовместимом существующем файле fallback запрещён. Release
остаётся только с MSI layout; обязательной зависимости не появилось.

В Debug host Poll пишет состояние optional helper на первом tick и раз в 30s,
без дополнительных таймеров/наблюдателей/попыток загрузки DLL. Это позволяет
отличить пропущенный startup от отсутствия сообщений из основного host loop.
После пересборки требуется штатный перезапуск платформы, чтобы уже работающий
host исполнял новый код (новая DLL на диске не заменяет загруженный модуль).
Для диагностики выбрать подсистему ReflectionProfiles без ограничения модуля.

### Новый профиль при открытой галерее GS

По уточнению пользователя: при подключении монитора на открытой DWM-странице GS
не сбрасывать выбор текстуры. DisplayChanged запускает serial page pipeline:
если для новой конфигурации уже есть валидный профиль — восстановить его рецепт;
иначе взять **последний применённый**, а не draft, рецепт и источник предыдущего
профиля, сгенерировать новый холст и применить его обычным Apply-конвейером.
Повтор ячейки остаётся в native pixels (ScalePercent переносится без изменений),
растяжение старого PNG не используется. Во время генерации сохраняется отметка
исходника в галерее, а кнопка «Настроить» недоступна
(`_pendingDisplayReflectionSource`). Если диалог уже открыт, он переживает смену
топологии: превью пересоздаётся, черновик остаётся, но не применяется.

### Компоновка Configure на нескольких экранах

Превью — одно широкое полотно всего виртуального рабочего стола, а не отдельные
карточки с наборами отражений. Подписи вынесены из области полотна: имя источника
занимает отдельную строку над ним (слева), общее разрешение и набор DPI — отдельную
строку под ним (справа, приглушённо). Поэтому ни одна подпись никогда не попадает
внутрь прямоугольника монитора или на их стык. При появлении имени используется
изменение прозрачности, а не видимости, чтобы превью не прыгало по высоте.

Поверх полотна для каждого монитора рисуется самостоятельная скруглённая рамка с
крупным номером дисплея Windows (1, 2, ...). Рамка уменьшена внутри своей области
на одинаковый отступ по всем сторонам, поэтому пропорции прямоугольника не
меняются, а между соседними прямоугольниками остаётся настоящий зазор. На общем
ребре мониторов не рисуется ничего, и рядом с ним нет второй рамки: именно поэтому
на стыке не появляется вертикальная линия. Зазор показывает фон диалога, а не
обои/отражение, чтобы граница читалась как граница устройства.
Отступ — только геометрия рамок: обои и отражение продолжают замощаться 1:1 по
всему холсту. Номер читается из `MONITORINFO.szDevice`, не зависит от сортировки
и не входит в канонический ключ профиля. Номер подписан на полупрозрачной
подложке, чтобы оставаться читаемым на любых обоях.

### Синхронизация с OpenGlass: одно правило для старта, hot-plug и Apply

Назначение GlassSettings — управлять OpenGlass. Поэтому применённое значение
`CustomThemeReflection` не «живёт своей жизнью»: при открытии страницы, при смене
конфигурации экранов и после явного Apply оно приводится к записи текущего профиля
одной и той же таблицей решений (`Shared::ReflectionProfiles::Decide` в
`GlassShared/include/ReflectionProfileApi.h`, зеркало
`ReflectionProfilePolicy.Decide` в `GlassSettings/Services/ReflectionProfilePolicy.cs`).
Правила живут в одном месте, поэтому GS одинаково работает с установленной
платформой и без неё, а optional Native-хелпер не заводит второй набор правил.

Термины, чтобы не путать сущности:

- **Профиль** — ключ конфигурации дисплеев `<width>x<height>_DPI<first>_<16 hex>`,
  посчитанный из полных прямоугольников и DPI мониторов. Порядок и физические ID не
  участвуют: один и тот же набор мониторов даёт один и тот же ключ.
- **Текущая конфигурация** — этот ключ, посчитанный прямо сейчас, при каждом чтении
  заново (`EnumDisplayMonitors` в PMv2-контексте).
- **Рецепт** — запись HKCU `Textured\Profiles\<key>`: исходник, его SHA256,
  параметры обработки и готовый PNG для этого ключа.
- **Готовое полотно** — PNG этого ключа, прошедший проверку: `Ready=1`,
  `Version=2`, размеры совпадают с профилем, SHA256 файла равен `OutputHash`.

Действия:

| Состояние | Действие |
|---|---|
| Полотно текущего профиля готово и уже применено | **None**: синхронизировать нечего |
| Полотно текущего профиля готово, применено другое (наш PNG другого профиля или чужое изображение) | **Adopt**: записать полотно текущего профиля |
| Полотна нет, применён наш PNG, рецепт текущего профиля пригоден | **Regenerate**: построить полотно по рецепту и применить его |
| Полотна нет, применён наш PNG, рецепта нет или исходник пропал | **Clear**: снять значение, OpenGlass использует системное отражение |
| Ничего не применено, полотна нет | **None**: ничего не генерируется |
| Применено чужое изображение (путь вне `ProgramData\OpenGlass\Presets\Textured`), полотна нет | **None**: чужой выбор не перезаписывается и не удаляется |

Правило простое: **целевое состояние OpenGlass — проверенное полотно текущего
профиля**. Оно записывается всегда, кроме случая, когда уже применено. Если полотна
нет, наше собственное значение не остаётся на экране: полотно строится заново по
рецепту, а без рецепта значение снимается — ровно как при отсутствии выбора
(«Системное отражение (по умолчанию)»). Чужое изображение не трогаем, пока для
текущего профиля нет полотна; когда полотно появилось — оно главнее, иначе OG
показывал бы картинку, которую GS не может учесть.

После изменения значения выполняется `ReloadRenderService.NotifyThemeChanged` (Native
адресует `WM_THEMECHANGED` окну `Dwm`), иначе запущенный OpenGlass продолжает
показывать прежний кадр. Baseline области отражений синхронизируется, поэтому ни
Adopt, ни Clear, ни Regenerate не выглядят как несохранённая правка. Порядок записи:
сначала значение в DWM, затем ownership (`Managed`, `ManagedOutput`) — последующий
`Read()` разрешается уже на новый профиль.

Страница показывает состояние явно: если для текущей конфигурации полотна нет, над
информационным блоком появляется плашка «нет готового полотна, OpenGlass показывает
системное отражение» с кнопкой **Сгенерировать полотно** (когда рецепт пригоден) или
сообщением, что исходник рецепта недоступен. На старте страницы генерация не
запускается сама — строится только уже проверенный PNG; кнопка запускает
`ReflectionTextureService.PrepareAsync` по сохранённому рецепту и затем ту же
синхронизацию.

Реализация в GS: `SynchronizeReflectionProfileAsync` (одна точка входа для `OnLoaded`
и для `RebindReflectionToDisplayAsync`), `ReflectionRenderState.ReadProfileRecord`,
`CanRegenerate`, `AdoptReadyProfile()`, `ClearAppliedProfile(active)`. Optional
Native-хелпер использует ту же таблицу; `Regenerate` он не выполняет — рендер живёт в
GS, поэтому в этом состоянии он снимает наше значение, чтобы OG не показывал
устаревшее полотно.

Ограничения: `Clear` не удаляет опубликованные PNG и записи рецептов других профилей;
ручной выбор текстуры и Apply не отменяются этой синхронизацией (она лишь применяет
полотно профиля, если оно уже готово).

Если диалог ещё не показан, но топология уже изменилась, начальная компоновка
перестраивается один раз при открытии хоста. Обрезка поверхности hosted-диалога
пересчитывается по фактическому `SizeChanged` самой поверхности: раньше она
обновлялась только из помощника границ и могла прочитать ширину до раскладки,
оставив узкую полосу без отрисовки при первом расширении панели.

При подключении, отключении или изменении настроек монитора диалог не
закрывается: превью пересоздаётся на месте, старый ряд экранов удаляется из
дерева (иначе в диалоге оставались бы два ряда — прежний с одним монитором и
новый с двумя), а значения редакторов и цвет остаются черновиком, предпочтительная ширина и границы хоста пересчитываются, полотно
перерисовывается. Декодирования, начатые для прежнего дерева, отбрасываются и не
могут опубликовать устаревший кадр. Если пересоздание не удалось, Apply
блокируется и показывается ошибка. Открытие диалога захватывает профиль один раз —
из снимка самого превью; Apply проверяет, что топология с тех пор не менялась.

Смена топологии автоматически переносит отражение на новое разрешение. Такой
перенос не должен выглядеть как несохранённая правка: после успешной публикации
нового полотна ключ `CustomThemeReflection` принимается в baseline, но только если
baseline всё ещё содержит прежнее автоматическое полотно, реестр содержит
ожидаемый новый PNG и запись профиля готова. Индикаторы пересчитываются из
снимка, поэтому остальные несохранённые параметры остаются dirty. Ручной выбор
текстуры, Configure/Apply, изменённые параметры и чужие значения остаются dirty,
как раньше.
