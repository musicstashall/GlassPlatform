# GlassSetup — Win32 / C++17

> **Безопасность тестирования:** Setup и GlassUnins запускаются с правами администратора, но не проверяют подлинность исполняемых файлов комплекта GlassPlatform по подписи или доверенным эталонам хэшей и не удостоверяют защищённость каталогов с помощью проверки их прав. Поэтому используйте только доверенные файлы и проверенные зарегистрированные пути; реальные установку и удаление проверяйте в изолированной Windows VM с контрольной точкой, не на рабочей установке.

Окно мастера установки GlassPlatform: **x86 (Win32)**, MSVC и WebView2. Деинсталлятор `GlassUnins` использует тот же автономный HTML и нативный резервный интерфейс. Пока HTML-контент грузится, и установщик, и деинсталлятор показывают индикатор ожидания; нативные элементы (в деинсталляторе — флажки продуктов) включаются только если WebView2 недоступен. Сборка выполняется через **`GlassProject.sln`**.

Это единая инструкция по сборке, установке, удалению и диагностике GlassSetup. Описание относится к текущим исходникам, а не является гарантией проверенного поведения Windows.

**Статус текущей ветки:** рабочая незавершённая переработка для проверки сборки, не готовый выпуск. Подробности и обязательные ограничения: [implementation-progress.md](docs/implementation-progress.md). Первичная установка оригинального MSI SecureUxTheme и переключение регистрации через Settings реализованы в исходниках; удаление оригинального продукта через GlassUnins, session/offline style reset и транзакционный cache controller ещё не завершены. Падения Explorer вне текущего scope.

Общий ярлык Settings при частичном удалении Setup/GlassUnins: [протокол и границы](docs/settings-shortcut-maintenance.md).

Макеты и UI-проверка без системных операций: [каталог и запуск preview](docs/mockups/README.md).

Версии карточек и независимый MSI ProductVersion: [контракт MSI-версий](docs/msi-product-versions.md).

## Текущее ограничение переходной ветки

Движок уже получает выбранные MSI из `packages\`, каталога EXE, пригодного Current или релиза; рабочая копия и downloads
находятся в защищённом ProgramData workspace. Подлинность local MSI подтверждается release hash либо подписью того же
сертификата, что у Setup. Неподписанный локальный файл не принимается автоматически по одному имени/GUID.

Наш `OpenGlass-x64.msi` подписывается существующим сертификатом Glass перед публикацией рядом с Setup.
DLL автора не переподписываются; оригинальный MSI SecureUxTheme остаётся неизменным. Неподписанный fallback не добавлен.
Фактическую подпись комплекта и offline trust ещё нужно проверить сборкой на Windows.
Embedded MSI/Native ещё остаются для старого inspector/native preflight, новый maintenance UI не подключён.
Это незавершённая ветка разработки, не готовый выпуск. См. начало implementation-progress.

## Переход на лёгкий установщик: build output и каталог релиза

Первый этап: после сборки **Release|x64 → Release|x86** проекты MSI дополнительно публикуют
`Glass-x64.msi`, `Glass-x86.msi`, `GlassSettings-x64.msi`, `GlassSettings-x86.msi`, `OpenGlass-x64.msi`
рядом с EXE в `Build\GlassSetup\Release`. Старые WiX output/resource inputs пока сохранены для работающего движка.
Runtime acquisition подключён; переход inspector/UI/cache/helper contract ещё не завершён. Полный список ограничений указан выше.

В Windows PowerShell из корня solution, после подписи финальных файлов:

```powershell
# Первый каталог: все пять MSI и EXE; версии MSI и EXE читаются из самих файлов.
.\GlassSetup\scripts\New-ReleaseCatalog.ps1 -ReleaseTag v1.4.3 -IncludeSetup
# Отдельный MSI в другом релизе: остальные версии/ссылки и EXE metadata сохраняются.
.\GlassSetup\scripts\New-ReleaseCatalog.ps1 -ReleaseTag settings-hotfix -Products settings64 `
    -BaseManifest .\Build\GlassSetup\Release\version.json
```

Скрипт создаёт `version.json` в том же output каталоге; проверяет MSI UpgradeCode/архитектуру, пишет ProductCode/PackageCode,
размеры и SHA-256. Не выполняет MSI, не подписывает файлы и не загружает их в GitHub. После изменения каталога нужно
опубликовать актуальный общий manifest и соответствующие assets. Исходный `BaseManifest` должен быть проверенным
последним каталогом; скрипт не получает его из сети и не подтверждает Authenticode доверие. Windows COM/MSI сценарий
генерации и новая публикация output ещё требуют проверки полной MSVC/WiX сборкой.

Portable проверки: `python GlassSetup/tests/run_package_catalog_tests.py` (для GCC/Clang также `--sanitize`).
Поддержка источников подключена к движку, но не считается проверенной Windows runtime установкой и не завершает весь план.

## Работа с исходниками в Visual Studio

1. Сохраните свою работу и проверьте **Изменения Git**. Не обновляйте файлы поверх несохранённых изменений и не применяйте Reset для получения обновлений.
2. Для продолжения этой работы выберите `arena/e53d8dd2-glassplatform` в **Git → Управление ветвями**; при первом открытии удалённой ветки используйте Checkout с отслеживанием. Не изменяйте `master` при диагностике.
3. **Извлечь (Fetch)** получает коммиты, но не обновляет рабочие файлы. **Получить (Pull)** обновляет выбранную ветку только опубликованными изменениями; локальные изменения другой машины и архивы автоматически не переносятся. При конфликте остановитесь и сохраните сообщение.
4. После обновления снова откройте решение и восстановите NuGet. Для проверки используйте новую сборку по указанному ниже пути, а не сохранённую копию EXE.
5. Для отмены отдельного опубликованного изменения найдите коммит в истории Visual Studio и используйте **Revert (Обратить)**: создаётся обратный коммит без удаления истории. Для серии коммитов сначала определите диапазон и сохраните свои изменения; не отменяйте вслепую весь рефакторинг.

## Сборка полного комплекта в Visual Studio

Нужны Visual Studio 2022 с C++ v143 и Windows SDK, .NET SDK, WiX/HeatWave и восстановленные пакеты NuGet. SecureUxTheme больше не собирается и не перепаковывается GlassPlatform: используются неизменённые MSI автора. Сборки `SecureUxThemeCa` и собственных SUT WiX-проектов удалены. Новых DLL нет: discovery/download встроены в GlassSetup; JSON разбирается vendored header-only nlohmann/json 3.12.0 (MIT).

### Оригинальный MSI SecureUxTheme

При выборе SecureUxTheme движок в своём worker, **до изменения системы**, ищет `SecureUxTheme_x64.msi` или `SecureUxTheme_x86.msi` в каталоге запущенного `GlassSetup.exe`, не в CWD. Resolver также распознаёт ARM64 asset по native machine; это не заявление о поддержке всего комплекта Glass на ARM64. На x64 ставится только x64 MSI автора, уже содержащий обе разрядности. Локальный поиск также учитывает `packages\` и пригодный Current.

- Вручную скачанный официальный v4.0.0 проверяется по зафиксированным размеру и SHA-256 без сети. Другой существующий MSI должен совпасть с asset текущего stable release; для этого требуется API. Неизвестный/повреждённый файл не перезаписывается.
- Если MSI отсутствует, `https://api.github.com/repos/namazso/SecureUxTheme/releases/latest` даёт stable tag и точные `browser_download_url`, `size`, `digest`. Отсутствующий asset/digest, prerelease, draft, неверный URL, HTTP/network error блокируют старт до системных изменений.
- Недостающий оригинальный MSI скачивается во временный `.part` защищённого ProgramData workspace, проверяется и используется через частную копию. Пользовательские файлы рядом с EXE/в `packages\` не изменяются. При ошибке/отмене `.part` убирается.
- Перед запуском создаётся неизменённая проверенная копия в защищённой временной рабочей папке; исходный файл на время проверки/копирования закрыт для записи/удаления. Проверяются ProductName, ProductCode из фактической MSI database, UpgradeCode и native architecture.
- Установка синхронно ожидается в worker с `INSTALLUILEVEL_NONE` и `REBOOT=ReallySuppress`; собственное окно MSI и автоматическая перезагрузка не запускаются. 3010/1641 дают сообщение о необходимости перезагрузки. Скачивание отменяемо; финальная vendor MSI-транзакция идёт после всех rollbackable регистраций Glass, когда отмена UI уже закрыта. Ошибка MSI откатывает Glass; после успеха MSI остаются только нефатальные операции запуска.
- Оригинальные ARP/ProductCode/системные пути не изменяются. Уже установленный официальный MSI распознаётся по UpgradeCode независимо от способа установки и сохраняется без скачивания, repair/upgrade и изменения включения. Старая перепаковка Glass требует отдельного явного перехода. Старые ProductCode сохранены исключительно для распознавания/существующего explicit removal.
- Системные файлы и MSI-регистрация принадлежат пакету автора. Его штатное удаление намеренно может оставить permanent ThemeUiProxy/COM redirect. Settings может отдельно снять регистрацию механизма, но не удаляет эти файлы и не подменяет MSI-деинсталляцию.

Текущий проверенный stable release: [v4.0.0](https://github.com/namazso/SecureUxTheme/releases/tag/v4.0.0); прямые ссылки: [x64](https://github.com/namazso/SecureUxTheme/releases/download/v4.0.0/SecureUxTheme_x64.msi), [x86](https://github.com/namazso/SecureUxTheme/releases/download/v4.0.0/SecureUxTheme_x86.msi), [ARM64](https://github.com/namazso/SecureUxTheme/releases/download/v4.0.0/SecureUxTheme_ARM64.msi). Online discovery не закреплён на v4: используется API latest.

### Роли и оставшиеся файлы SecureUxTheme

- **GlassSetup** скачивает и устанавливает оригинальный MSI. MSI-инвентаризация не зависит от того, запустил пакет GlassSetup или пользователь вручную.
- **GlassSettings** только **включает/отключает регистрацию**: Winlogon IFEO и native/WOW COM InProcServer32 на ThemeUiProxy. При отключении COM возвращается к штатному themeui.dll, свои IFEO-токены снимаются, чужие токены и биты сохраняются. Файлы, MSI-продукт, запись удаления и источники MSI не удаляются. Убраны старые механизмы копирования DLL, cleanup.cmd и отложенного удаления через задачу.
- **Удаление продукта** — задача MSI/удалятеля, а не переключателя Settings. Оригинальный MSI сейчас можно удалить через Windows «Установленные приложения». Перевод **GlassUnins** на динамическую идентичность оригинального MSI ещё не завершён; его нельзя считать реализованным этим изменением.

В Setup удаление оригинального SecureUxTheme сейчас поддержано только для
однозначно подтверждённого установленного MSI без загруженного hook: **Inactive**
или **ActivationPending**. Ожидание первой загрузки не запрещает удаление. Для
активного, ожидающего выгрузки, стороннего или конфликтного состояния корзинка
открывает конкретное объяснение отказа и не меняет план. Полное удаление активного
компонента пока не реализовано; повторная проверка после reboot не гарантирует,
что он окажется неактивным. Техническая MSI-инвентаризация остаётся в журнале.

**Важно:** после штатного удаления оригинального MSI автор намеренно оставляет некоторые постоянные файлы proxy, а COM-перенаправления могут сохраняться. Это не доказательство установленного MSI и не повод автоматически удалять файлы вручную. Отключение через Settings также оставляет файлы намеренно — оно не является удалением продукта.

Обнаружение разделено на независимые факты:
1. MSI зарегистрирован — продукт установлен, но это **не означает**, что переключатель включён.
2. Патчер и proxy лежат на диске, регистрация снята — механизм выключен, файлы сохранены, конфликта только из-за файлов нет.
3. Остался только proxy без патчера — он не позволяет включить SecureUxTheme. Если осталось COM-перенаправление, Settings позволяет снять его; это отдельное состояние остаточной регистрации, не «внешняя установка».
4. IFEO/COM зарегистрированы — переключатель отражает регистрацию. Уже загруженные хуки живут до перезагрузки: полное отключение требует перезагрузки Windows. Не следует путать это с немедленной выгрузкой DLL из чужих процессов.
5. Чужой COM-сервер, неподдерживаемые типы значений или активный pre-v4 hook — самостоятельный конфликт; автоматической перезаписи/чистки нет. Один неактивный legacy DLL сам по себе не считается активным hook; однако его наличие может блокировать запуск v4 MSI по условию самого автора.

Включение проверяет наличие и PE-разрядность полного native/WOW комплекта, не копируя его. Модули на время регистрации открыты без разрешения записи/удаления. Перед отключением активного механизма Native требует подтверждённый штатный visual style, независимо от предварительной подготовки GUI. Значения реестра проверяются до записи и повторно перед каждым изменением; при ошибке восстанавливаются исходные значения. Чужие конкурентные изменения не затираются. Это не crash-durable registry transaction: принудительное завершение процесса/сбой питания требует повторной проверки состояния. Доступ к WRP-ключам идёт через scoped backup/restore privileges без смены владельца/DACL.

**Остаётся:** предупреждения доступности на карточке и завершение GlassUnins/Windows VM проверки MSI, WRP-привилегий,
COM, active styles и reboot. Единственный постоянный кэш — `Current`; отдельный постоянный SecureUxTheme каталог
не вводится. Provider уже ищет `packages\`, рядом с EXE и Current, а download остаётся в защищённом workspace до публикации.

1. Откройте `GlassProject.sln`; при запросе перезагрузите изменённые проекты и выполните **восстановление пакетов NuGet**. Если решение было открыто во время Pull, надёжнее закрыть и снова открыть его, чтобы обновились зависимости проектов.
**Порядок сборки зафиксирован: Release | x64 → Release | x86.** Предварительная сборка отдельных проектов не требуется. GlassUnins первого прохода встраивает только уже собранный x64 helper. Финальный GlassSetup второго прохода содержит обе Native DLL; при установке он сохраняет x86 helper в защищённый maintenance cache для работы Unins на 32-битной ОС независимо от наличия GlassSettings.

2. Выберите **Release | x64** и соберите всё решение. Этот проход создаёт x64-компоненты, `GlassSettings.Native.dll`, деинсталлятор и три x64 MSI.
3. Затем выберите **Release | x86** и снова соберите всё решение. Он создаёт x86 MSI и `Build\GlassSetup\Release\GlassSetup.exe` с пятью встроенными MSI и обеими версиями `GlassSettings.Native.dll` для Unlocker.

Используются пять SDK-style WiX-проектов. `global.json` закрепляет `WixToolset.Sdk` **6.0.2**, NuGet-источник задан в `nuget.config`. Для работы с `.wixproj` в обозревателе Visual Studio может понадобиться расширение **HeatWave Community Edition**; для MSBuild из командной строки оно не обязательно. Не запускайте миграцию SDK-style проектов WiX как проектов WiX v3. Не добавляйте `PackageReference` для самого `WixToolset.Sdk`. Для установки HeatWave: **Extensions → Manage Extensions → Online**, затем закройте все окна VS и откройте решение заново. Если проект отображается как несовместимый после обновления, восстановите NuGet и перезагрузите решение; при необходимости закройте VS и удалите только её локальный кэш `.vs`.

MSI имеют конечный OutputPath сразу `Build\GlassSetup\Release\<имя проекта>.msi`: `Glass-x64`, `Glass-x86`, `GlassSettings-x64`, `GlassSettings-x86`, `OpenGlass-x64`. Это выход самих WiX-проектов, а не post-build копия из `Build\GlassSetup\msi`. Signing работает с этим же `TargetPath`. WiX obj/tracking и project-private BaseOutputPath находятся в `Cache\<имя проекта>`, чтобы Clean не владел общей папкой Setup/MSI. Native/payload staging не меняет конечный MSI output. Setup не встраивает MSI/Native в RC; `GlassUnins.exe` остаётся embedded ресурсом, оригинальный SecureUxTheme — внешний MSI автора. Порядок сборок solution остаётся Release|x64 → Release|x86.

Порядок важен: Release-сборка использует общую сессию версии комплекта. Отдельная сборка x86 Setup без результатов x64 не содержит необходимые ресурсы. При необходимости отменить незавершённую сессию:

```bat
msbuild GlassProject.sln /t:GlassBundleCancelSession /p:Configuration=Release /p:Platform=x64
```

`Release | Any CPU` не является сборкой полного установочного комплекта. Не меняйте архитектурные привязки проектов для обхода двух проходов. В проходе x64 сам Setup не собирается; x86-проход использует ранее созданные x64 MSI. `GlassSettings` публикуется для MSI в `Build\<архитектура>\Release\GlassSettings\`; отдельный WiX-проект внутри VS требует готовой публикации. Staging/harvest выполняется в `Build\SetupPayload\...`. Ссылка Setup на x86 Native задаёт порядок сборки, но не линкует его import-библиотеку; вложенная сборка x64 WiX из Setup не выполняется.

**Проверка встроенного Native:** runtime preflight читает x86/x64 DLL прямо из RCDATA текущего GlassSetup.exe и проверяет PE-разрядность и реальные экспорты. Уже установленный GlassSettings для этой проверки не нужен. Исправлена ошибка, при которой x64 проверялся по пути установленного Settings, хотя сообщение называло DLL встроенной. Если ресурс действительно повреждён, журнал теперь указывает architecture, resource ID, конкретный check и Win32 error; соответствие ProductVersion само по себе не доказывает наличие экспорта.

**Контроль состава:** существование MSI и проверка протокола Native не доказывают свежесть всего payload. Перед испытаниями сравните версии/даты DLL в `Build\x64\Release` и `Build\x86\Release`, MSI, итоговый Setup и манифесты `Build\GlassBundleSession.json`, `Build\GlassBundles\<версия>.json`, если они созданы. Номер Setup или MSI может отличаться от ProductVersion вложенных DLL; такой комплект требует выяснения причины до публикации. При ошибке сохраните полный **Вид → Вывод → Сборка** обоих проходов. Не исправляйте манифесты и счётчики вручную. Перед новой пересборкой для расследования падения сохраните DLL вместе с соответствующими PDB: следующая сборка может их перезаписать.

Для отдельной Debug-сборки из Developer Command Prompt:

```bat
msbuild GlassProject.sln /t:GlassSetup /p:Configuration=Debug /p:Platform=x86
```

Результат — `Build\GlassSetup\Debug\GlassSetup.exe`, промежуточные файлы — `Cache\GlassSetup\Win32\Debug\`. Debug не заменяет Release-проверку MSI.

Компоненты контекстного меню лежат в подкаталоге платформы **`GlassShellSparse\`** (`GlassShellExt.dll`, `GlassShellHost.exe`, `GlassShellSparse.msix`, `AppxManifest*.xml`, `Assets\`) — это и OutDir проектов `GlassShellExt`/`GlassShellHost` (`Build\<arch>\Release\GlassShellSparse\`), и ExternalLocation sparse-пакета на целевой машине (`GlassSetupPayload.targets` копирует подкаталог целиком). MSIX подписан **тем же сертификатом разработчика** `CN=Stanislav K.`, что и все PE (`GlassShellExtSignPaths` в `GlassShellExt.vcxproj` → `Shared/GlassSign.targets`); отдельного «разработческого» сертификата больше нет, `Publisher` манифеста равен Subject сертификата, семейство пакета — `GlassProject.GlassShellMenu_83517z3ecdax2` (`GlassShellMenuConstants.h`, проверка `tests\sparse_identity_mock.py`). Публичный сертификат `DeveloperCodeSigning.cer` и инструкция `DeveloperCodeSigning.txt` (RU/EN) ставятся в корень платформы.

Сертификаты никто не создаёт и не экспортирует; в хранилище сертификат разработчика попадает **только по явному выбору пользователя** и только одним кодом — `ShellSparsePackage::TrustSparseSigner` (`LocalMachine\TrustedPeople`, подписант установленного `GlassShellSparse.msix`, Subject обязан равняться `CN=Stanislav K.`). Windows 11 регистрирует sparse-пакет только от издателя, сертификат которого есть в «Доверенных лицах» (иначе `0x800B0109`), поэтому Setup на Windows 11 x64 — если подписант собственного `GlassSetup.exe` ещё не доверен (`QuerySelfSignerInfo`: WinVerifyTrust либо отпечаток в CurrentUser/LocalMachine `TrustedPeople`) — показывает после выбора компонентов отдельную страницу **«Сертификат разработчика»** (`Page::Certificate`, `IDS_CERT_*`): что такое сертификат, зачем он нужен (только компактное меню Windows 11), Subject/отпечаток SHA‑1/срок/хранилище и два варианта; по умолчанию «установить». Кнопка «Установить» — на этой странице (на странице компонентов тогда «Далее»). После установки файлов и первого старта платформы (точка невозврата) выбранное доверие выставляет помощник `rundll32 GlassSettings.Native.dll,GlassSettings_ShellSignerTrustSetupV1W /installroot "<root>"` (код 0 — добавлен/уже доверен, `0x47535400|SparseSignerTrustResult` — ошибка → заметка `IDS_WARN_CERT_INSTALL` со ссылкой на GlassSettings; отката нет), затем регистрируется меню. При отказе или без страницы (Win10, уже доверен, x86) помощник `GlassSettings_ShellExtRegisterSetupV1W` после неудачи sparse-пути регистрирует **классический** `IContextMenu` **только через `regsvr32 /s GlassShellExt.dll`** (`DllRegisterServer`; пункт после «Показать дополнительные параметры») и возвращает код `0x47504C00|причина` — для Setup это успех с замечанием на странице «Готово» (`IDS_WARN_SHELL_CLASSIC_CERT`: назван сертификат, путь к `.cer` и ссылка «Установить сертификат разработчика» в GlassSettings → Система; иные причины — `IDS_WARN_SHELL_CLASSIC_OTHER`). Никакие `shellex`/`ContextMenuHandlers`/`InprocServer32` ключи вручную не пишутся — см. правило в `GlassShellExt/README.md`. Конфликт внешнего каталога (`0x47504346`) fallback не получает — существующая регистрация сохраняется. Любая неудача регистрации оболочки или установки сертификата не откатывает установку: продукты остаются установленными и запущенными. EULA (раздел 5 RU/EN) описывает сертификат, его назначение и право отказаться; **GlassUnins сертификат никогда не удаляет** (удаление — вручную через `certlm.msc` → «Доверенные лица»; описано в EULA и `DeveloperCodeSigning.txt`). Также проверьте наличие совместимых VC++ Runtime (x64 и x86): встроенный `GlassSettings.Native.dll` может использовать динамическую CRT.

Проверка установленного `GlassSettings\GlassSettings.Native.dll` для helper использует штатные Windows ACL: допускает привилегированные SYSTEM/Administrators/TrustedInstaller и не считает inherit-only `CREATOR OWNER` правом записи в текущий объект. Проверяются файл и все предки без изменения их прав, архитектура/нужные экспорты, Authenticode и совпадение издателя с Setup; writable для непривилегированного пользователя или reparse-пути не допускаются. Строгая политика приватного ProgramData-кэша к MSI-owned каталогам не применяется. Отказ helper до запуска мешает обоим вариантам меню и сам по себе не свидетельствует о проблеме сертификата; смотрите `Native helper` / `Native trust` в журнале. Если сертификат уже доверен, страница предложения импорта не показывается и существующее доверие не меняется.

При чистой и повторной установке Setup по умолчанию регистрирует GlassShellExt для пользователя, от имени которого он запущен. На Windows 11 существующий sparse-пакет принимается без изменений только при совпадении пользователя, семейства и внешнего каталога (`<root>\GlassShellSparse\`), исправном состоянии и проверяемом манифесте с нужным пунктом меню; занятые/непроверяемые регистрации сохраняются без изменений, а установка завершается с замечанием на странице «Готово» (регистрация выполняется уже после точки невозврата, см. ниже). Удаление через Setup/GlassUnins ограничено текущим пользователем и снимает и sparse-пакет, и классическую регистрацию. Проверка и регистрация не атомарны; условия доверия сертификату по-прежнему определяются Windows. Миграции со старого семейства пакета (`…_t6mpd150h6a5c`, dev-сертификат) нет — платформа в тестировании, переустановка начисто.

Authenticode: `Shared/GlassSign.targets` (импорт из `Directory.Build.targets`) в Release подписывает выход каждого PE-проекта после Build, publish `GlassSettings.exe` после Publish и каждый MSI после Build; `GlassSetup.exe` подписывается последним, а перед компиляцией ресурсов `GlassSetupVerifyEmbeddedMsi` проверяет подписи встраиваемых MSI и `GlassSettings.Native.dll` (`Invoke-GlassSign.ps1 -Mode Verify`). С ключом автора в `CurrentUser\My` неподписанный payload и любая ошибка подписи — ошибка сборки; без ключа — предупреждение `GSIGN001`/`GSIGN106`, и собирается неподписанный комплект (сборка контрибьютора). Режимы `GlassSign=Local|Require|Skip` (Debug всегда `Skip`; офлайн — `GlassSignNoTimestamp=true`); пин отпечатка — `GlassSignThumbprint`. После создания или смены ключа нужен **Rebuild** обеих фаз (Release|x64, затем Release|x86): инкрементальная сборка не переподписывает неизменившиеся файлы. Перед публикацией: `Shared\scripts\Test-GlassSignatures.ps1`. Контракт для пользователей и отпечаток — корневой README, «Подпись сборок». Не путайте Authenticode PE/MSI с отдельной подписью sparse MSIX.

**Внешние MSI при чистой Release-установке.** Запускайте `Build\GlassSetup\Release\GlassSetup.exe` вместе с MSI выбранных компонентов в том же каталоге (также поддерживается подкаталог `packages`). Отсутствие установленных продуктов не отменяет проверку пакетов: нужны правильные ProductCode/UpgradeCode, архитектура и версия, а также подпись того же издателя, что у запущенного Setup, либо проверенный хэш из release-каталога. Подпись локального MSI проверяется Windows Authenticode/SIP; кроме успешного результата допускается **только** `CERT_E_UNTRUSTEDROOT` при точном совпадении отпечатка сертификата с Setup. Это позволяет использовать комплект автора на чистом ПК без предварительного импорта self-signed сертификата; хранилища не изменяются. Ошибки целостности, срока, назначения сертификата, иные ошибки цепочки, чужой издатель и неподписанные локальные MSI не допускаются. Неподписанная contributor-сборка не становится доверенной от соседства файлов. Для скачивания в релизе должны быть опубликованы сами MSI и соответствующие записи нового `version.json`; одного Setup и старого манифеста недостаточно. При отказе выбора источника показываются проверенные пути и причина отказа для каждого; код Authenticode и результат проверки издателя записываются в `GlassSetup.log`.

**Явное удаление в Setup.** На установленных карточках Platform x64/x86, GlassSettings x64/x86 и OpenGlass кнопка корзины добавляет `Remove` в общий план. Снятая обычная отметка означает **Keep**, не удаление; действие можно отменить до запуска. В одном плане допускаются Remove одних Glass-продуктов и install/update/repair других. Для Remove не нужен новый MSI из релиза: используется проверенный снимок установленного пакета и его MSI-регистрации. План повторно проверяет фиксированные семейства, machine context, корни и snapshot непосредственно перед изменениями. Чистое удаление не запрашивает release-каталог и не создаёт новые пользовательские списки настроек.

Задачи обеих Platform, прежние задачи/служба OpenGlass и общий ярлык предварительно проверяются/сохраняются. Очистка task/shortcut обратима; удаление службы — последний fallible шаг до commit. Удалённые продукты не запускаются заново, их источники не публикуются в новом Current; remaining ARP refresh сохраняется. Файлы/регистрации MSI и task/shortcut восстанавливаются существующим rollback при ошибке до commit; отказ восстановления не объявляется успехом, backup сохраняется. Меню нативной Platform снимается проверенным установленным Native до удаления его файлов; при откате предпринимается повторная регистрация. Это восстановление работоспособности принадлежащего этому root меню, а не доказательство точного восстановления прежнего compact/classic варианта; реальная Windows-проверка обязательна. Для удаления нативной Platform нужен совместимый GlassSettings той же разрядности (его установку/ремонт можно включить в этот же план); иначе операция отказывается до остановки хостов.

Если удалить GlassSettings, оставив соответствующую Platform, показывается отдельное подтверждение риска по архитектуре; отмена возвращает в план без изменений. Не возникает принудительного каскада удаления. Авторский сертификат не удаляется. Профильные данные не очищаются этим действием. **Ограничение:** original SecureUxTheme и managed Glass Remove выполняются отдельными операциями; UI объясняет ограничение и блокирует Apply, backend независимо отказывает такому смешению до изменений. Это сохраняет commit-last контракт авторского MSI и службы. Debug по-прежнему симулирует выбранные действия, реальный Remove проверяется только Release в Windows VM.

Для Debug выбирайте **Debug | x86**: сам `GlassSetup` и его `GlassShared` всегда 32-битные. В конфигурации решения Debug | x64 установщик не участвует в автоматической сборке. **Debug симулирует установку и откат, Release выполняет реальную установку из внешних MSI.** Разделение задаётся `_DEBUG`, а не наличием embedded payload. Симуляция Debug не запускает InstallEngine и не меняет продукты. `--demo-tour` в Debug дополнительно включает автоматический просмотр страниц; это отдельный режим, не обязательный для обычной симуляции. Для проверки имитации отката запустите Debug без `--demo-tour` и подтвердите отмену на разных процентах. За время подтверждения ширина полосы сохраняется; имитация отката занимает около пяти секунд. Реальный Release проверяйте в изолированной Windows VM с внешними MSI: завершение и откат определяются результатом engine, а не таймером. `GlassUnins` в решении собирается как Release|Win32.

Для отдельной проверки раннего окна запустите Debug с аргументом `--debug-slow-startup`: фоновая подготовка специально задерживается примерно на четыре секунды. Сначала должен появиться «бублик» по центру содержимого; окно должно перетаскиваться и закрываться через `X` или Escape во время задержки. Если анимации Windows отключены, индикатор неподвижен в соответствии с системной настройкой. Аргумент действует только в Debug; уберите его после проверки. До окна Windows может показать стандартный запрос UAC — он не управляется установщиком.

## Пути установки и проверка прежних установок

Если запись пути продукта отсутствует, на 64-битной Windows используются системные папки `Program Files\GlassPlatform` для x64 и `Program Files (x86)\GlassPlatform` для x86; на 32-битной Windows — системный Program Files с `\GlassPlatform`. Диск определяется Windows. При наличии зарегистрированного пути соответствующая платформа использует его, в том числе корректный нестандартный каталог. GlassSettings находится в подпапке `GlassSettings` выбранной платформы. OpenGlass использует свой зарегистрированный `OpenGlassInstallPath`; при отсутствии записи — подпапку `OpenGlass` корня x64. Выбора папки в мастере нет.

Для платформы приоритет чтения — архитектурное значение `HKLM\Software\GlassPlatform\InstallPathX64` или `InstallPathX86` в представлении соответствующей разрядности, затем машинное `InstallPath` в том же представлении, затем архитектурное значение HKCU. Для x86 на x64 последним проверяется прежнее `HKCU\Software\Wow6432Node\GlassPlatform\InstallPath`; для нативной архитектуры — `HKCU\Software\GlassPlatform\InstallPath`. Для OpenGlass приоритет — `HKLM\Software\StanislavKa\GlassPlatform\OpenGlassInstallPath`, тот же путь в HKCU и затем `HKCU\Software\StanislavKa\OpenGlass\InstallPath`. Выбранные источник и путь выводятся в журнал. Значения из команды задачи или расположения старого деинсталлятора не выбираются как целевой путь. Для регистрации и снятия регистрации оболочки Setup и GlassUnins передают выбранный путь Native-помощнику явно; при отсутствии файлов по этому пути он не подбирает другой каталог. На 32-битной Windows допускается штатный вызов `regsvr32` для `GlassShellExt.dll` из выбранного корня.

Отсутствующую запись можно создать в ходе установки; существующие конфликтующие копии Setup специально не согласует. Пустой, некорректный или недоступный зарегистрированный путь не заменяется молча системным. Ошибочная запись, например указывающая на каталог сборки проекта, при этой политике может стать целевым путём. До настоящей установки убедитесь, что используемые записи действительно содержат нужные каталоги; Setup их автоматически не исправляет.

Для отсутствующего x64-пути 32-битный процесс на x64 Windows получает системный Program Files из `ProgramFilesDir` и `ProgramW6432Dir` в 64-битном представлении системного HKLM и проверяет их согласованность. Недоступные и небезопасные системные каталоги блокируют операцию.

Перед остановкой хостов Setup проверяет известные регистрации и видимые связанные коды продуктов, cached MSI, контекст, зарегистрированные пути компонентов и действия задач/службы; GlassUnins проверяет выбранные продукты и задействованные задачи/службу. Пути MSI за пределами соответствующего выбранного корня, отсутствующие сведения, неоднозначный контекст, неподдерживаемые таблицы MSI, посторонние команды задачи/службы, ссылки/reparse points в проверяемых путях или несколько жёстких ссылок на проверяемый файл приводят к остановке с диагностикой. Проверки повторяются перед важными MSI-операциями; при обнаружении проблемы в ходе установки запускается откат, насколько это безопасно.

Если расположение или версию ранее зарегистрированной платформы надёжно определить не удалось, мастер не объявляет её повреждённой и не предлагает удалять файлы: он прекращает работу с диагностикой. Проверки пути и PE-формата сами по себе не устанавливают происхождение или подлинность DLL. Проверка происхождения и подлинности файлов, а также защищённости каталогов не реализована; выполнять установку или удаление следует только с доверенными файлами в тестовой VM.

Проверки и операции не являются единой атомарной транзакцией: изменения другими процессами, hard links, неизвестные сторонние продукты и установки других пользователей полностью не исключены. При сомнении не удаляйте файлы, задачи или записи MSI/реестра вручную: сохраните журнал и обратитесь за помощью. Независимый OpenGlass в общем каталоге следует проверять только на VM с контрольной точкой.

## Изменение состава установленного комплекта

На странице выбора показано состояние каждого продукта и действие: установленный отмеченный продукт будет обновлён, отсутствующий отмеченный — установлен, снятый установленный остаётся как есть. **Setup ничего не удаляет**: флажок означает только «выполнить действие с продуктом», удаление продуктов выполняется исключительно через GlassUnins. Цветные этикетки обозначают установку зелёным, обновление жёлтым, сохранённый без изменений продукт — нейтральной синей этикеткой «Установлено»; если продукт отсутствует и не выбран, этикетки нет. Основная платформа разрядности Windows обязательна и обозначена замком. На 64-битной Windows отсутствие x86 отключает эффекты и возможности платформы в 32-битных приложениях; отсутствие GlassSettings означает ручное изменение параметров в реестре. Предупреждения показываются только когда продукт не выбран **и** не установлен; оба отображаются одновременно.

Состояние определяется по известным текущим и прежним MSI-кодам GlassSetup. Независимая установка OpenGlass может не распознаваться, а общий каталог пока не защищён от возможной перезаписи. Сценарии с самостоятельно установленным OpenGlass проверяйте только на VM с контрольной точкой.

Перед изменениями Setup сохраняет доступные старые MSI, файлы и относящиеся к установке значения реестра. Так как Setup не удаляет продукты, задачи, ярлык и служба невыбранных продуктов не затрагиваются; резервные копии задач и службы (`GlassInstallRemoval::Prepare/Commit/Restore`) мастером больше не используются и остаются только в общей библиотеке. На время установки мастер останавливает обе разрядности платформы и OpenGlass; после установки хосты **невыбранных** сохранённых продуктов (платформа другой разрядности, OpenGlass) запускаются снова, если работали при открытии мастера, а выбранные запускаются стадией запуска. Кнопка, Escape и `X` до точки невозврата по-прежнему запускают кооперативную отмену и откат. Если файлы, MSI или связанные записи не удалось восстановить, мастер не запускает ранее остановленные хосты поверх неполного набора.

### Пользовательские значения по умолчанию

Перед регистрацией задач автозапуска (до точки невозврата) Setup записывает в куст пользователя, от имени которого он запущен, списки процессов платформы: `HKCU\Software\StanislavKa\GlassPlatform\AttachList` (REG_DWORD на исполняемый файл: 0 — запрещено, 1 — только всплывающие окна, 2 — полностью) и `…\BlockList` (REG_DWORD 1 на исполняемый файл плюс пояснительное значение по умолчанию). Источник данных один для всех проектов — `GlassShared\include\DefaultProcessLists.h`. Список записывается только если его ключа нет или в нём нет ни одной записи; существующие списки при обновлении не меняются. Отказ записи — замечание на странице «Готово», не откат; при откате установки списки, созданные этим запуском, удаляются. Setup работает с повышением прав, поэтому при запуске из-под другой учётной записи администратора (UAC с вводом чужих учётных данных) значения попадают в куст той учётной записи, а не вошедшего пользователя. Планируется: при восстановлении установки эти списки перезаписываются, а остальные значения ключа пользователя удаляются до состояния чистой установки.

Завершающая стадия разделена точкой невозврата. До неё (запись пользовательских значений по умолчанию, регистрация задач автозапуска и службы OpenGlassHost, проверка их действий и путей) любой отказ по-прежнему ведёт к откату: ничего ещё не запущено. Первый запуск платформы фиксирует установку: после него откат не выполняется ни при каких условиях. **Выбранная платформа запускается всегда** — независимо от того, работала ли она и была ли включена её задача при запуске мастера; отключённую задачу `StartPlatform` включает сам. Для обеих разрядностей правило одинаково. Отказы последующих шагов — платформа не сообщила о запуске за отведённое время, задача/пути изменились между проверкой и запуском, OpenGlass не стартовал, ранее работавший хост не перезапущен, регистрация оболочки отклонена или сохранена из-за конфликта — записываются в журнал (`Finish note: …`) и показываются списком на странице «Готово» в варианте «готово, есть замечания» с подсказкой, что делать дальше. Эти замечания не меняют результат установки и не требуют повторного запуска мастера. Созданная резервная копия сохраняется в `Windows\Temp\GlassRollback-*`, её путь показывается в деталях; журнал и копию следует сохранить. Откат не может вернуть несохранённые документы закрытых приложений, историю выполнения задач, изменения других процессов или гарантировать восстановление после аварийного выключения.

Состояние OpenGlass фиксируется вскоре после появления первого окна мастера. Если его файлов тогда не было, выбранный OpenGlass запускается после установки. Если файлы уже были, он запускается только когда работал при открытии мастера; отдельный более поздний снимок служит для отката. Состояние определяется по фактическому статусу службы и запущенным экземплярам подходящей задачи, включая отключённые, но работающие объекты; само наличие файлов, включённой задачи или окна системного DWM **не означает**, что OpenGlass запущен. Если служба и задачи остановлены, Setup не посылает остановку и не ждёт её. Если состояние нельзя надёжно определить, установка останавливается до изменения пакетов. Если ранее не работающий хост появился после снимка, Setup не останавливает его и просит начать заново.

Если команда остановки уже отправлена, при отмене мастер сначала даёт ей завершиться, чтобы запоздалая остановка не выключила восстановленный хост. После этого он возвращает только состояние, которое действительно изменил. Работающую отключённую службу мастер пытается запустить с восстановлением её прежнего типа запуска; отключённую старую задачу автоматически включать нельзя. Если несколько подходящих задач или экземпляров не позволяют однозначно восстановить ранее работавший хост, Setup отказывает до остановки. Сторонние и неоднозначные конфигурации нужно проверять отдельно; `GetInstances` показывает только экземпляры, доступные контексту безопасности вызывающего.

До резервной копии и остановки хостов Setup проверяет разрядность и версионированный экспорт встроенных Native DLL (`GlassSettings_InstallerScanProtocolV2`; после загрузки x86-копия должна ответить на рукопожатие значением `GSI2`), читая PE-файл без загрузки и выполнения DLL. Если файл отсутствует или не поддерживает нужный протокол, установка прекращается до изменения продуктов. Это предварительная проверка сборки, а не сам мониторинг процессов.

После распаковки, резервной копии и остановки платформы с ожиданием исчезновения её мьютексов мастер сначала устанавливает выбранный GlassSettings. Состояние x86/x64 платформы определяется её мьютексом, а не фактом существования/включения задачи. Остановка идёт через общий координатор `Shared::GlassStop`: он посылает `StopEvent` и ждёт, пока хост сам снимет хуки и выгрузит модули (окно **15 с**); если хост ушёл — задача Планировщика не останавливается вовсе, её `IRegisteredTask::Stop(0)` остаётся резервом и применяется только к живому хосту, после чего мастер ждёт закрытия мьютекса (до 45 с). Тот же путь использует GlassUnins с собственным `Reason::Uninstaller`. На этой стадии установщик сам не запускает принудительную выгрузку модулей; она остаётся отдельной последующей проверкой с подтверждением. Обработка `WM_CLOSE` зависит от уже установленной версии хоста, поэтому её поведение при обновлении следует проверять отдельно. Пустой результат первоначального обнаружения не отменяет последующего мониторинга при установке поверх. На установке с нуля этап сканирования модулей пропускается (`Unlocker: clean install - module scan skipped`): платформы, её задач и служб ещё нет, держать `Glass*.dll` некому. Если GlassSettings снят, его MSI на этом этапе не запускается. Затем из защищённого временного каталога загружаются встроенные DLL комплекта: x86 — в Setup, x64 — в `rundll32` на 64-битной Windows. Они используют существующий сканер и Unlocker `GlassSettings.Native`, без отдельного сканера в Setup; по завершении операции временные библиотеки освобождаются и удаляются. Если файл не удаётся удалить сразу, попытка удаления после перезагрузки и ошибка фиксируются в журнале. При установке поверх ошибка или неполный результат проверки блокируют продолжение; перед отказом локальный скан повторяется один раз, а причина записывается в журнал (`stage=<этап> pid=<PID> exe=<процесс> gle=<код> flags=…`; x64-помощник передаёт её строкой `#fail`). При `ERROR_ACCESS_DENIED` сканер однократно включает `SeDebugPrivilege` повышенного процесса и повторяет открытие — так проверяются процессы других учётных записей и сеансов. x86-сторона под WOW64 не считает ошибкой недоступный ей `explorer.exe` (на 64-битной Windows он всегда 64-битный): такой процесс отмечается в журнале и остаётся x64-скану, который проверяет Explorer сам и при невозможности отказывает. Если остаются модули, мастер спрашивает разрешение на выгрузку, повторно сканирует и при необходимости показывает страницу закрытия процессов; остальные MSI запускаются только после освобождения модулей. Отмена или ошибка на странице мониторинга откатывает раннюю установку GlassSettings, не перезаписывая ещё занятые файлы платформы. Explorer и сам мастер не завершаются и не выгружаются принудительно; для Explorer отправляется штатный запрос освобождения, а после подтверждения могут закрываться только окна файлового менеджера. Если модули всё ещё заняты, установка ожидает дальнейших действий пользователя или отмены.

`GlassSetup` — Win32, поэтому для x64 используется `Sysnative\rundll32.exe`, а не `System32` с WOW64-перенаправлением. Временная x86-копия имеет отличительное имя `GlassSetup.Native.x86.dll`; после загрузки Setup сверяет фактический путь и ответ протокола. Журнал позволяет отличить несовместимый встроенный файл, неверный загруженный путь и ошибку ответа DLL. Перед запуском также проверяется экспорт `GlassSettings_UnlockerW`; колбэк Rundll32 может передать аргументы как ANSI, поэтому парсер поддерживает и ANSI, и UTF-16. `GlassSettings.exe` не игнорируется: мастер отдельно добавляет его в список занятых процессов и предлагает штатное закрытие без принудительной выгрузки. При неполной проверке установку продолжать нельзя.

## Нереализованная логика и отложенные решения

Это оставшийся объём работ, а не описание уже работающих функций.

|---|---|
| Подлинность файлов | Нет единой проверки происхождения, доверенной подписи или эталонных хэшей перед выполнением файлов комплекта. Проверка PE, экспорта и пути этого не заменяет. Отдельная задача должна охватить GlassSettings, GlassShellExt, при необходимости GlassCompat и связь с подписью платформы. |

| Подпись выпуска | Authenticode PE/MSI/Setup и sparse MSIX подписываются автоматически одним сертификатом разработчика, но пока временным self-signed (SmartScreen: «Неизвестный издатель»; компактное меню Win11 только после ручного импорта `.cer` в «Доверенные лица», иначе классический fallback); переход на SignPath в CI не выполнен. |
| Единый кэш | Не разработан единый защищённый кэш комплекта, его доверие, обновление и очистка. Текущие временные каталоги, резервные копии и cached MSI Windows Installer не являются таким механизмом. |
| Независимый OpenGlass | Нет согласованного обнаружения и обновления/переноса независимой Inno-установки как отдельного владельца файлов. Общий каталог может быть перезаписан. Политика сосуществования пока не выбрана. |
| Пропуск неизменившихся продуктов | Нет согласованной политики пропуска переустановки по совпадению версии/хэшей. Это отдельное решение, а не обещанная оптимизация. |
| Полный снимок ShellExt | Нет полного сохранения и восстановления произвольного прежнего состояния sparse/legacy-регистраций оболочки. Снимок отдельных значений и консервативный отказ при конфликте не заменяют такую транзакцию. |
| Регистрация ShellExt в режиме разработки | Нет безопасного автоматического разрешения существующей loose development registration: даже работающий пакет может быть признан непроверяемым и блокировать повторную установку. Не предусмотрено автоматическое удаление чужих пользовательских регистраций и миграция старого семейства пакета. |
| Идентичность процессов | Карта использует PID и имя: повторное использование PID процессом с тем же именем не распознаётся надёжно. Отсутствующие PID скрываются из списка, но их слоты не освобождаются этим фильтром из-за гонки с новой записью; полной стратегии очистки и уникальной идентичности нет. |

Централизованное управление, жизненный цикл общего движка и миграция существующих точек входа пока не реализованы; варианты описаны ниже. |

### Единый управляющий процесс удаления: целевая схема

**Принятое направление, пока не реализовано:** сохранить отдельные пункты удаления для каждого установленного продукта — платформы x64, платформы x86, GlassSettings и OpenGlass — в «Установленных приложениях». При этом удалением управляет один общий процесс, а не несколько независимо работающих мастеров. На машине отображаются только установленные продукты; альтернативные MSI GlassSettings x64/x86 не должны создавать две записи одного приложения.

Отдельная запись продукта и отдельная полная копия программы удаления — не одно и то же. Каждая запись должна оставаться самостоятельной точкой входа с правильным именем, иконкой и командами `UninstallString` / `QuietUninstallString`, передающими идентификатор продукта общему управляющему процессу. Выбранный продукт задаёт начальный запрос, но не обходит правила зависимостей и подтверждения удаления связанных компонентов.

Варианты реализации, между которыми ещё предстоит выбрать:

1. **Один общий EXE.** Все записи продуктов запускают один установленный менеджер удаления с аргументом продукта (например, `--product <код>`). Полные копии мастера в каталогах каждого продукта не нужны.
2. **Отдельные небольшие точки входа под общим управлением.** Для каждого продукта сохраняется совместимый `unins000.exe`-launcher/stub, который передаёт запрос общему менеджеру и не содержит собственного полного движка удаления. Это позволяет сохранить прежние пути запуска; независимые полные мастера параллельно не выполняются.

Обе схемы сохраняют отдельные пункты в списке Windows. Объединение всех продуктов в единственную запись удаления не является целевой схемой. Переход на Burn также не выбран: он требует отдельного решения и сам по себе не заменяет требование сохранить продуктовые точки входа.

Требования к будущей реализации:

- Один управляющий процесс ведёт UI, подтверждения, остановку платформы, отдельную стадию Unlocker, последовательность MSI, журналирование и обработку ошибок. Это процесс на время операции, а не требование создать постоянно работающую службу.
- Повторный запуск из другого пункта Windows не начинает конкурирующее удаление: запрос передаётся активному менеджеру либо пользователю явно сообщается о занятой операции. Порядок обработки нескольких запросов и IPC-протокол ещё нужно определить; новый запрос не считается согласием удалить дополнительные продукты.
- Общий движок должен оставаться доступным после удаления любого одного продукта, включая GlassSettings и платформу одной разрядности. Нужно определить его защищённое расположение, владельца установки, обновление, версионную совместимость и удаление после последнего зависимого продукта. Нельзя просто дать нескольким MSI независимо устанавливать и удалять один общий EXE.
- Существующие регистрации и команды удаления должны мигрировать без потери точек входа; ошибка обновления не должна оставлять продукт без работающего удаления. Совместимость старых `unins000.exe` / `unins000.dat`, quiet-режим, права администратора, проверку IPC-запросов и доверия к исполняемому движку нужно спроектировать и проверить отдельно.
- Выборочное удаление, зависимости продуктов, сохранение пользовательских файлов и правила InstallPath/MSI-guard остаются обязательными. Один управляющий процесс сам по себе не добавляет полного транзакционного отката MSI или восстановления после аварийного завершения.

**Текущая реализация отличается:** полноценный GlassUnins включается в MSI как `unins000.exe`; используются код продукта и `unins000.dat`, а часть общей логики вынесена в GlassInstallSupport. Общая кодовая база и аргумент `--product` ещё не означают, что все точки входа обслуживаются одним управляющим процессом.

### Открытые дефекты и неподтверждённое поведение

- **Explorer:** падение при обновлении остаётся открытым дефектом. Дамп показывает недопустимое чтение в диапазоне текущего TaskbarCompat и выгрузку/повторную загрузку модулей; тот же диапазон раньше занимал WndCompat. Без соответствующих DLL/PDB не установлено, является ли это ошибкой TaskbarCompat или оставшимся адресом старого обработчика. Не считать причину доказанной по одному имени сбойного модуля.
- **Остановка и Unlocker:** в исходниках используется остановка проверенной задачи Планировщика; запущенная пользователем сборка с сообщением `SignalPlatformStop` не подтверждает проверку этого пути. Для нового пути ожидается `stopped via Task Scheduler`. Уже установленный старый хост сохраняет собственное поведение остановки. Безопасность остановки, снятия PLM-debugging и повторного подключения в Windows пока не подтверждена.
- **Пустое сканирование:** страница разблокировки появляется только при оставшихся holders. Пустой результат не гарантирует снятие всех callbacks/подклассов/ссылок и безопасность повторного подключения. Дамп после автозапуска не доказывает, что сканер пропустил DLL ранее. Требуется проверка полного жизненного цикла модулей, а не искусственный показ страницы или увеличение задержки.
- **Состав комплекта:** проверка согласованности версии Setup/MSI с фактически упакованными x64/x86 DLL недостаточна. При несовпадении нужны Output сборки и манифесты; причина несвежего payload пока не установлена.
- **Оставшиеся каталоги Unins:** причина наблюдавшихся пустых каталогов не установлена. Логика безопасной очистки присутствует; для диагностики нужны полные пути, экран результата и журналы, а не ослабление защиты от ссылок вслепую.
- **ShellExt:** фактическое появление меню после переустановки, активация Explorer, конфликтующие/старые пакеты, несколько пользователей и восстановление после отказа требуют Windows-проверки. Вызовы проверки, регистрации и удаления не атомарны.
- **Регрессии интерфейса и отката:** отсутствие краткого системного окна MSI, все способы отмены, ранняя установка GlassSettings, завершение GlassUnins, точное восстановление прав, задач/служб и файлов требуют полного прогона в VM. Успешные переносимые mock/source-тесты не доказывают интеграцию MSVC/WiX, C#/WinRT и Windows Installer. Пользовательская сборка и один прогон установки также не закрывают эти проверки.

### Преднамеренные границы текущей схемы

- Выбора каталога в UI нет: зарегистрированный InstallPath является источником истины, иначе используются системные каталоги. Конфликтующие записи не исправляются автоматически; MSI-guard для файлов за пределами выбранного корня сохраняется.
- WebView2 Runtime не включён в комплект: Setup предлагает онлайн-загрузку или закрытие, нативные страницы служат резервным представлением. Автономной установки Runtime нет.
- Пока `unins000.exe` включается в MSI как полный мастер. Целевое направление — отдельные продуктовые точки входа под единым управляющим процессом; общий EXE или небольшие launcher/stub ещё предстоит выбрать. Миграция не реализована, переход на Burn не выбран.
- Откат не возвращает несохранённые документы закрытых приложений и не отменяет изменения посторонних процессов.

## Проверка перед публикацией

Сначала проведите проверку **в тестовой Windows VM с контрольной точкой**. Автотест исходников не выполняет настоящих MSI-операций и не доказывает работоспособность отката:

```bat
python GlassSetup\tests\verify_resources.py
```

Дополнительно `GlassSetup\tests\selection_tests.cpp` проверяет правила выбора продуктов, `removal_order_tests.cpp` — порядок операций, `progress_tests.cpp` — полосу установки и отката, `unlock_state_tests.cpp` — возврат к слайдам, `empty_directories_tests.cpp` — безопасный обход пустых каталогов. Это независимые C++17-тесты без Windows SDK. Python-сценарии `*_mock.py` в той же папке проверяют исходные инварианты или компилируют с GCC/Clang фрагменты реального кода с имитацией Win32/COM; для них нужны Python 3 и g++ (или `CXX` с другим совместимым компилятором). Эти проверки не выполняют настоящий C#, задачи, службы, регистрацию оболочки или MSI на Windows. `system_roots_mock.py` проверяет системные каталоги для 32-битного процесса на x64/x86; `registered_paths_mock.py` — выбор путей и приоритет реестра; `preserve_registry_mock.py` — сохранение существующих пользовательских записей MSI; `installed_version_mock.py` — определение версии. `shell_install_root_mock.py` проверяет передачу выбранного пути компоненту оболочки и отказ от поиска в других каталогах. `unlock_root_mock.py` проверяет использование выбранного x86-пути для разблокировки при удалении. `unins_close_state_mock.py` проверяет закрытие после успеха и ошибки, а также запрет закрытия во время удаления MSI. Папка `GlassSetup/tests` хранится в репозитории и сохраняется при обычном слиянии веток; тестовые исходники не входят в установочные MSI.

Проверку путей и реальных MSI-операций выполняйте **только в изолированной VM** с контрольной точкой. В Release-журнале сравните `Startup installation roots`, источники путей, `Startup MSI registrations`, `Preflight` и `Target x64=… x86=… OpenGlass=…` с записями соответствующих продуктов. Проверьте чистую установку без записей, повторную установку с разными нестандартными путями, разные значения HKLM/HKCU без их согласования, несовпадение расположения MSI с выбранным корнем, изменённую задачу или службу, ссылки, ошибки доступа и отмену с откатом. Контрольные файлы вне выбранного каталога при отказе не должны изменяться. Не создавайте и не исправляйте тестовые регистрации на рабочей машине.

Если конфликт обнаружен уже после начала последовательности MSI в GlassUnins, часть продуктов может быть удалена; деинсталлятор не обещает полного отката после начала удаления. Сохраняйте журнал и используйте контрольную точку VM. После полного и выборочного удаления проверьте, что на странице результата работают кнопка «Закрыть» и системный `X`; во время выполнения необратимых MSI-операций закрытие запрещено.

Проверьте раннее окно и закрытие при загрузке, отсутствие WebView2, повторный запуск и резервный нативный интерфейс; также проверьте DPI на нескольких мониторах. В тестовой VM проверьте на x64 и, если поддерживается, x86 Windows: чистую установку с разными комбинациями; обязательную платформу системной разрядности; предупреждения при отказе от x86 и GlassSettings, в том числе оба сразу; видимость продуктов в «Установленных приложениях»; выборочное удаление и зависимые продукты; старт и сохранение отключённых задач.

На VM сначала установите все продукты. Убедитесь, что при старте настоящей Release-установки отдельное окно Windows Installer «Подготовка к установке» не появляется; проверка только в Debug-имитации для этого недостаточна. При повторном запуске снимите OpenGlass, завершите установку и убедитесь, что его MSI, служба `OpenGlassHost` и задачи `OpenGlass Host` / `OpenGlass Legacy Host` **остались на месте** (Setup ничего не удаляет; карточка показывает «Установлено · без изменений»). Верните контрольную точку и отдельно повторите для x86 (задача `GlassPlatform.Win32 Autorun Task (x86)` и её состояние не меняются) и GlassSettings (оба возможных MSI и ярлык сохраняются); проверьте также одновременное снятие всех трёх. Удаление продуктов проверяется только через GlassUnins. Отдельно проверьте запуск платформы: при обновлении с остановленной платформой и отключённой задачей после установки обе выбранные разрядности должны работать, а задача — быть включена; в `HKCU\Software\StanislavKa\GlassPlatform` должны появиться `AttachList` (64 записи) и `BlockList` (21 запись) на чистой установке, а при обновлении существующие списки не должны измениться. Повторите для прежних MSI и для отдельной чистой установки на пустой VM.

На VM отдельно проверьте освобождение занятых модулей кнопкой «Повторить» и, если нужно, разблокировку процессов: пока операция выполняется показывается её экран, после успешного освобождения и продолжения установки снова показываются слайды. Проверьте также чистую установку с оставшимися модулями, отказ x64-помощника, занятый GlassSettings и отмену во время сканирования: MSI не должен начаться при неполном результате. Проводник и мастер не должны принудительно завершаться. Если модули всё ещё заняты, должно появиться следующее подтверждение, а не слайды.

Отдельно проверьте OpenGlass: первую установку без файлов; переустановку, когда он был запущен при открытии мастера; переустановку, когда был остановлен; изменение состояния после открытия мастера; отключённую службу и старую задачу. При остановленной службе и остановленных задачах, даже если обычное окно DWM существует, не должно быть ни команды остановки, ни ожидания её тайм-аута; уже остановленный OpenGlass не должен запуститься при отмене. Для работающей службы и работающей задачи проверьте штатную остановку, отмену во время неё и восстановление именно прежнего состояния. Повторите при открытом подтверждении отмены, если операция успела завершиться ошибкой: подтверждённая отмена должна приводить на страницу отмены, а не на страницу прежнего тайм-аута; настоящий сбой восстановления должен оставаться заметным. Для очистки проверьте пустые и непустые каталоги, пользовательские файлы, нестандартные и вложенные пути, ссылки и отмену после удаления. Сравните с контрольной точкой, включая пустые каталоги оставленных продуктов.

На обновлении и чистой установке проверьте отмену через кнопку, Escape и `X` во время распаковки, снимка, Unlocker, удаления и установки MSI. Дождитесь окончания отката и сравните файлы, записи MSI, реестр, XML/права/состояние задач и конфигурацию службы с контрольной точкой; отдельно проверьте задачи с сохранённым паролем, чужим действием и недоступными правами — до изменения пакетов должна появиться понятная ошибка. Убедитесь, что страница запуска показана не менее пяти секунд.

Закрытие сторонних процессов в Unlocker может привести к потере их несохранённых данных; откат не запускает эти приложения и не возвращает их документы. Регистрацию старых/осиротевших shell-компонентов и восстановление прав файлов также проверяйте отдельно; непроверенный программный откат не заменяет контрольную точку VM.

При сбое отката сохранённая резервная копия остаётся в защищённом каталоге `Windows\Temp\GlassRollback-*`; её путь указывается в логе/деталях ошибки. **Не удаляйте резервную копию до выяснения причины.** Системный откат после аварийного выключения, принудительного завершения процесса или перезагрузки требует отдельной проверки; для восстановления тестовой машины используйте контрольную точку VM.

## Журналы и отладка

- `%WINDIR%\Temp\GlassSetupLogs-*`: `GlassSetup.log` и подробные MSI-журналы; удаление прежней версии и повторная установка дописываются в соответствующий журнал.
- Публикация maintenance cache пишет строки `Maintenance cache:`: этап (`stage`), путь, операция, код в hex/decimal и причина. Коды Win32/MSI/HRESULT помечены отдельно от отказа внутренней проверки (`Policy`); при отказе owner/DACL записываются SID и маска прав. Первая ошибка сохраняется в подробностях итогового предупреждения даже при последующем отказе восстановления. Замечание о кэше само по себе **не означает ошибку запуска продуктов**.
- `%WINDIR%\Temp\GlassUnins-*`: рабочая копия деинсталлятора (`unins000.exe`), из которой он и работает, пока удаляются MSI. После завершения работы копия и её каталог удаляются; хвосты прошлых запусков убираются при следующем старте деинсталлятора с записью `Stale private copies: removed=… busy=…`. Журналы лежат отдельно и не удаляются.
- `%WINDIR%\Temp\GlassUninsLogs-*`: `GlassUnins.log` и `GlassInstallSupport.log` деинсталляции. При перезапуске деинсталлятора могут создаться два каталога — посмотрите последние по времени. Если остались каталоги, сохраните их полные пути и строки `Empty-directory cleanup` / `Marked empty directory` из `GlassInstallSupport.log`: они показывают попытку очистки и ошибки; отметка об удалении может означать отложенное удаление из-за открытых дескрипторов.
- Эти каталоги доступны администраторам и SYSTEM. Если они не созданы, запись журналов отключена: небезопасный `%TEMP%` как запасной путь не используется.
- Если MSI завершился успешно, а проверка модулей всё равно завершилась ошибкой, это разные этапы. Для диагностики нужны строки `Watch:`, включая запрошенный/загруженный путь, экспорты и ответ протокола; одно сообщение об ошибке протокола само по себе не доказывает, какая DLL была загружена и почему.
- При ошибке сборки приложите полный текст **Вывод → Сборка** в Visual Studio, конфигурацию, разрядность, версию Windows и шаг воспроизведения. При ошибке выполнения также приложите журналы и скриншот. Если падает Explorer, сохраните событие «Ошибка приложения» и/или Windows Error Reporting из **Просмотр событий → Журналы Windows → Приложение** за то же время: нужны имя сбойного приложения и модуля, код исключения и время. Перед отправкой удалите персональные данные и секреты.

WebView2 Loader (x86) статически находится в `third_party/`. Мастер предлагает загрузить Microsoft Edge WebView2 Runtime при его отсутствии; деинсталлятор может показать страницы в нативном резервном режиме.

## Дополнительные детали движка

- Статус каждой разрядности GlassPlatform определяется по мьютексу. Работающая задача проверяется и останавливается через `IRegisteredTask::Stop(0)`; `S_FALSE` и ошибки не считаются подтверждением остановки. Если платформа уже остановлена, запрос не отправляется. После попытки остановки мастер ждёт исчезновения мьютекса и отдельно проверяет остаточные модули; проверка задачи и вызов Stop не атомарны.
- Выбранный GlassSettings устанавливается раньше мониторинга; если он снят, его MSI не вызывается. Встроенные версии Native извлекаются во временные каталоги с ограниченными правами, а не из незащищённого каталога пользователя. Для x86 Setup применяет существующий Native export; для x64 — resident `GlassSettings_UnlockerW /watchGlassModulesSetup`, при повторной проверке `/scanGlassModulesSetup`; для принудительной выгрузки предусмотрен `/forceUnload`. Обычные старые команды без `Setup` остаются частью Native API. Пассивное ожидание само по себе не должно принудительно выгружать чужой процесс.
- На странице занятых модулей согласие требуется до выгрузки. Explorer не завершается и не выгружается принудительно; для него допускаются мягкий запрос и закрытие окон файлового менеджера. После успешного освобождения возвращаются слайды. Другие процессы закрываются только после соответствующего подтверждения. Несохранённые данные закрытых приложений откатить нельзя.
- `GlassInstallMsi.cpp` вызывает `MsiInstallProductW` / `MsiConfigureProductExW` при `INSTALLUILEVEL_NONE`; ProductCode читается через `MsiOpenDatabaseW`, не через открытие установочной сессии. Подробные логи относятся к Windows Installer API. Не заменяйте это скрытым запуском GUI `msiexec.exe` как способом убрать окно «Подготовка к установке».
- Снимок включает доступные cached MSI, деревья файлов и выбранные значения реестра; для удаляемых продуктов дополнительно сохраняются поддерживаемые определения и права задач, ярлык и ветка службы. Во время отката MSI используется `GLASS_RESTORE_NO_CAB=1`; условие `InstallFiles` сравнивается с `1`, поскольку строка `"0"` сама по себе истинна в условиях MSI. Доступность cached MSI, полное сохранение ACL и паролей/контекста задач нужно проверять на Windows. При неподдерживаемой конфигурации мастер должен остановиться до изменения MSI.
- Для ошибки пользователь видит страницу мастера. Подтверждённая отмена при успешном восстановлении приводит на страницу отмены; если восстановление реально не удалось, показываются детали и сохраняется резервная копия. Ошибка, возникшая пока открыто подтверждение отмены, не должна вытеснять подтверждённую отмену прежним сообщением тайм-аута.
- Дизайн: логический размер окна **1000×600** при 96 DPI, контент 544 и футер 56. `res/slideshow.html` использует локальный origin `https://glassplatform.invalid/` и встроенные ресурсы. Таймер прогресса — 16 мс. Отмена фиксирует последнюю видимую ширину; левый край остаётся на месте, правый постепенно уменьшается. Завершающая страница запуска длится не менее пяти секунд.
- Нативный стиль кнопок использует Detours и `DrawThemeTextEx` / `DTT_TEXTCOLOR`. Не подменяйте `WM_PAINT`/`WM_PRINTCLIENT` кнопок: это ломает штатную анимацию `comctl32`. Деинсталлятор использует общие части `GlassInstallSupport`, но имеет отдельные ограничения отката после начала необратимого удаления.
- Debug без встроенных MSI выполняет примерно 30-секундную имитацию; около пяти секунд имитируется откат. Это не проверка реальной MSI-транзакции. Конфигурация `Debug | x86` и отдельная тестовая VM для Release обязательны для соответствующих видов проверки.

## OpenGlass: владение установкой, реестр и диагностика

### Независимый официальный установщик OpenGlass

Независимый Inno Setup от ALTaleX531 имеет собственную запись в «Установленных приложениях». Пример идентификатора записи — `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\{D3D1BC7D-5E24-4B33-9383-7934271A3B05}_is1`; идентификатор и версия могут отличаться. В записи могут присутствовать `DisplayName`, `DisplayIcon`, `InstallLocation`, `UninstallString`, `QuietUninstallString` и ссылка на репозиторий OpenGlass.

**Ограничение:** Setup пока не распознаёт эту независимую Inno-запись как свой MSI и не имеет согласованной политики её обновления или переноса. Общий каталог с такой установкой может быть перезаписан. Не проверяйте этот сценарий на единственной рабочей машине; используйте VM и контрольную точку. Не удаляйте запись или файлы стороннего установщика вручную в качестве автоматического шага.

### Текущий OpenGlass MSI GlassSetup

| Область | Фактическое поведение исходников |
|---|---|
| MSI / расположение | `OpenGlass-x64`, per-machine. Setup передаёт зарегистрированный `OpenGlassInstallPath`; если он отсутствует, используется `OpenGlass` внутри выбранного корня x64. Команда задачи не задаёт целевой путь. |
| Видимость | Шаблон не задаёт скрывающий `ARPSYSTEMCOMPONENT`; запись должна быть видна в «Установленных приложениях». Иконка MSI из `GlassSetup\res\app.ico`; ссылки Help/About ведут на репозиторий OpenGlass. |
| Удаление | MSI содержит `unins000.exe` и `unins000.dat`. После установки Setup пытается заменить ARP `UninstallString` / `QuietUninstallString` на собственный `GlassUnins` с кодом продукта. Работу каждого пункта Installed Apps надо проверить в Windows. |
| Modify / Repair | После MSI Setup записывает `NoModify=1` и `NoRepair=1` в ARP. Выбор состава выполняется мастером Setup или GlassUnins. |
| Текущий путь OpenGlass | MSI пишет `HKLM\Software\StanislavKa\GlassPlatform\OpenGlassInstallPath = [INSTALLDIR]`; Setup заполняет отсутствующие значения `OpenGlassInstallPath` и `InstallPath` в соответствующих разделах; существующие конфликтующие копии специально не согласуются. |
| Старый путь OpenGlass | `HKCU\Software\StanislavKa\OpenGlass\InstallPath` читается, если оба значения `OpenGlassInstallPath` отсутствуют, и очищается при удалении; заново он не записывается. Совместимость со сторонним ПО, зависящим от него, не подтверждена. |
| Путь платформы | Платформенные MSI используют `HKCU\Software\GlassPlatform\InstallPathX64` или `InstallPathX86`; Setup также обрабатывает машинные и прежние значения. Не предполагайте, что один общий `HKCU\Software\GlassPlatform\InstallPath` всегда указывает на x64. |

`PlatformPaths.cs` ищет DLL по значениям `Software\StanislavKa\GlassPlatform`, известным кандидатам комплекта и пути `<корень платформы>\OpenGlass\OpenGlass.dll`. Это обнаружение приложением отличается от выбора пути Setup по записям установки.

### Проверка путей перед изменениями

Setup проверяет контекст и реальные пути компонентов известных MSI; перед установкой также проверяет видимые связанные продукты. Действия задач и путь службы `OpenGlassHost` должны соответствовать выбранному каталогу. При постороннем или непроверяемом MSI, неожиданной команде задачи/службы, ссылке/reparse point, нескольких жёстких ссылках на проверяемый файл или недостаточных правах установка останавливается с диагностикой; повторные проверки выполняются перед важными операциями и при откате. GlassUnins проверяет выбранные MSI и задействованные задачи/службу. В отдельных случаях позднего изменения конфигурации часть удалений может уже состояться.

Проверки не подтверждают происхождение DLL и не атомарны с MSI/Task Scheduler/SCM; они не гарантируют защиту от параллельных изменений, hard links и неизвестных продуктов другого пользователя. Проверка подлинности исполняемых файлов не реализована; используйте только доверенные файлы и проверенные зарегистрированные пути. Не исправляйте подозрительные пути удалением файлов или записей вручную: сохраните журнал, а при ошибке отката — резервную копию. Проверяйте сценарии на VM с контрольной точкой.

### Как Setup определяет состояние OpenGlass

1. Состояние запуска сохраняется вскоре после открытия окна мастера. Перед изменениями создаётся отдельный снимок для отката.
2. Работа службы `OpenGlassHost` проверяется по фактическому `QueryServiceStatusEx`, а старые задачи `OpenGlass Host` / `OpenGlass Legacy Host` — по запущенным экземплярам Task Scheduler, в том числе в подпапках. Отключённая, но работающая служба/задача считается работающей.
3. Если служба и задачи остановлены, Setup не посылает им остановку и не ждёт тайм-аут. Окно класса `Dwm` и само наличие файлов или включённой задачи не свидетельствуют о работе OpenGlass. Если управляемых службы/задачи нет, отдельно проверяется процесс `OpenGlassHost.exe`: неизвестный вручную запущенный хост не останавливается автоматически, если его нельзя безопасно восстановить.
4. Если работающий хост появился после сохранения состояния, Setup останавливается и предлагает начать заново. Несколько подходящих работающих задач/экземпляров могут сделать откат неоднозначным — Setup в таком случае не пытается их остановить. Видимость экземпляров задачи зависит от контекста безопасности вызывающего.
5. Если остановка уже послана, при отмене Setup ждёт её завершения, затем пытается восстановить ранее работавший хост. Ранее остановленную службу или задачу он не запускает из-за отмены. Реальная ошибка восстановления остаётся ошибкой, а не маскируется как успешная отмена.
6. После успешной установки выбранный OpenGlass стартует при первой установке, если его файлов не было при открытии мастера. При переустановке — только если он тогда работал. Это правило не разрешает автоматически включать отключённую legacy-задачу; неоднозначные внешние конфигурации требуют проверки.

### Проверка на тестовой Windows VM

Создайте контрольную точку тестовой VM. В **Параметры → Приложения → Установленные приложения** проверьте отображение выбранных продуктов и их выборочное удаление. Записи в контексте соответствующего пользователя и администратора можно посмотреть без их изменения:

```bat
reg query "HKLM\Software\StanislavKa\GlassPlatform" /v OpenGlassInstallPath /reg:64
reg query "HKCU\Software\StanislavKa\GlassPlatform" /v OpenGlassInstallPath
reg query "HKCU\Software\StanislavKa\OpenGlass" /v InstallPath
sc query OpenGlassHost
schtasks /Query /TN "OpenGlass Host" /V /FO LIST
schtasks /Query /TN "OpenGlass Legacy Host" /V /FO LIST
```

Отсутствие HKCU-значения или одной из задач возможно. Команды с `/TN` проверяют указанное имя; для задач в подпапках смотрите дерево **Планировщика заданий**. Сравните фактический статус службы/задачи с поведением Setup: остановленные не должны ждать; работающие должны остановиться; подтверждённая отмена должна вернуть прежнее состояние. Повторите с отключённой службой, отключённой задачей, доступными и недоступными правами, а также при изменении состояния между открытием и началом установки.

При сбое сохраните `%WINDIR%\Temp\GlassSetupLogs-*`; при ошибке отката не удаляйте `%WINDIR%\Temp\GlassRollback-*`. Если падает Explorer, сохраните событие «Ошибка приложения» с именем модуля, кодом исключения и временем. Личные данные и секреты перед передачей удалите.

### Проверка зарегистрированных каталогов платформы (только чтение)

```bat
reg query "HKLM\Software\GlassPlatform" /v InstallPathX64 /reg:64
reg query "HKLM\Software\GlassPlatform" /v InstallPathX86 /reg:32
reg query "HKLM\Software\GlassPlatform" /v InstallPath /reg:64
reg query "HKLM\Software\GlassPlatform" /v InstallPath /reg:32
reg query "HKCU\Software\GlassPlatform" /v InstallPathX64 /reg:64
reg query "HKCU\Software\GlassPlatform" /v InstallPathX86 /reg:32
```

На 32-битной Windows не используйте `/reg:64`. Отсутствующая запись допустима; эти команды не создают и не исправляют значения. Полный приоритет, включая прежние HKCU-записи, указан в разделе о путях. Если источники противоречат друг другу, сохраните журнал; не запускайте MSI для «автоматического исправления» вне выбранного корня.

### Дамп Explorer и совместная отладка

Сохраните оригинальный `.dmp`, журналы за тот же запуск, версии Windows и пути реально запущенного Setup. Перед пересборкой скопируйте соответствующие x64 DLL и PDB из `Build\x64\Release` (TaskbarCompat, WndCompat, GlassCompat, GlassCore, ExplorerCompat). PDB от другой сборки нельзя подставлять как совпадающий: сравниваются CodeView GUID/Age. Контекст исключения и таблицы загруженных/выгруженных модулей важнее одного имени «сбойного модуля»; слова, похожие на адреса на стеке, без unwind не являются достоверным стеком вызовов. Дамп может содержать персональные данные — передавайте его только доверенному получателю, не добавляйте в публичный Git.

### SecureUxTheme: версия доступного предложения

Checking показывает проверенную ProductVersion соседнего canonical MSI
(для x64 — `SecureUxTheme_x64.msi`) и отдельно GitHub release. Если локального
пакета нет, числовая версия из GitHub подписана «релиз» и не считается проверенной
MSI ProductVersion. Checking не скачивает MSI и не создаёт рабочую копию;
Prepare повторно проверяет защищённый snapshot после явного Apply.
Подробнее: [версии отдельных MSI](docs/msi-product-versions.md).
Красные, жёлтые и зелёные HTML-карточки сохраняют доминирующий цвет при hover.
Макеты с демонстрационными версиями: [каталог GlassSetup](docs/mockups/index.html).
Новые изменения не проверены сборкой MSVC/WiX или установкой на Windows.

### SecureUxTheme: runtime-состояние и перезагрузка

Ожидание активации после первой установки не блокирует удаление. Setup повторно
проверяет unloaded state на Prepare, построении плана и перед MSI. Проверки точного
ProductCode, machine context, baseline/hash и запрет небезопасных смешанных операций
сохранены. Полное удаление уже загруженного hook пока не реализовано.

В [оригинальном v4.0.0 Package.wxs](https://github.com/namazso/SecureUxTheme/blob/v4.0.0/Package.wxs)
`ScheduleReboot` безусловный. После успешного MSI Setup уточняет рекомендацию по
свежему native runtime-состоянию: удалён и не загружен — без reboot notice;
установлен, ещё не загружен — требуется reboot; установлен и уже активен — новая
перезагрузка не запрашивается. Сырой MSI result сохраняется в журнале. 1641 не
снимается; неизвестное состояние и непрочитанные/существующие отложенные операции с системными файлами SecureUxTheme не позволяют
подавить vendor reboot request. Однозначно посторонние записи общей очереди не
приписываются SecureUxTheme; неоднозначный путь/формат остаётся консервативным отказом. Чужие pending операции
не очищаются. Проверки с mock API не заменяют Windows install/remove/reinstall VM.


### Зависимость удаления SecureUxTheme от Native

Планирование удаления учитывает доступное обновление GlassSettings разрядности
ОС: сначала пользователь явно добавляет обновление GlassSettings, затем удаление
SecureUxTheme. Без prerequisite карточка остаётся установленной, сверху появляется
жёлтое уведомление. При отсутствии **обеих** версий GlassSettings допускается
удаление с красным уведомлением о ручной подготовке темы и ответственности;
предупреждение закрепляется в сводке плана, полный текст доступен в «Подробнее».
Уведомления живут до следующего клика в любой области окна, но не менее 1000 мс.
Движения мыши, клавиатура и прокрутка не закрывают уведомление.
Подробный [контракт зависимостей и исключения](docs/cache-profile-maintenance-contract.md)
также описывает проверку MSI, разрядность, отмену prerequisite и порядок выполнения.
