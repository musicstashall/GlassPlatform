# Публикация релиза GlassPlatform

Инструкция для агента, когда пользователь просит опубликовать уже собранный комплект или отдельные его файлы. Ручные ворота сборки, подписи и проверки на Windows — [release-checklist.md](release-checklist.md). Смысл версий — [msi-product-versions.md](msi-product-versions.md). Подпись — [docs/signing.md](../../docs/signing.md).

Скрипт каталога только читает файлы и пишет `version.json`. Он ничего не заливает на GitHub.

## Когда применять

- «опубликуй установщик», «опубликуй пакеты», «замени файлы в релизе»;
- новый комплект, если пользователь прямо просит выпустить его и номер комплекта уже есть в сборке.

Платформу не запускать и не останавливать. Процессы не завершать. Новую сборку не начинать: публикуются файлы, которые пользователь уже собрал и подписал. Коммит и push — только по отдельной просьбе.

## Куда публикуется

| | |
|---|---|
| Репозиторий | `musicstashall/GlassPlatform` |
| Каталог файлов | `Build\GlassSetup\Release\` |
| Наши файлы | `Glass-x64.msi`, `Glass-x86.msi`, `GlassSettings-x64.msi`, `GlassSettings-x86.msi`, `OpenGlassResources-x64.msi`, `GlassSetup.exe`, `version.json` |

Официальные установщики OpenGlass и SecureUxTheme в этот каталог и в список файлов релиза не входят. В заметках на них остаются ссылки на релизы авторов.

Пока пользователь говорит, что версия комплекта не меняется, тег и заголовок остаются прежними. Их берёт текущий релиз на GitHub, а не следующий свободный номер. Новую сборку Release|x64 ради следующего номера комплекта не запускать.

Новый тег создаётся только по прямой просьбе выпустить новый комплект. Если `gh release create` отвечает, что тег уже есть, релиз не создают второй раз. Поле `isLatest` у `gh release view --json` не существует; список релизов — `gh release list`. Старый релиз удаляется только по прямой просьбе.

## Что писать версией

| Место | Откуда число |
|---|---|
| Заголовок релиза и первая строка заметок | комплект GlassPlatform, как в теге: `GlassPlatform 2.0.0.0115` |
| `GlassSetup.exe`, поля `setup` и `setupPackage.version` | числовой FileVersion EXE (`FileMajorPart`…`FilePrivatePart`), не ProductVersion |
| `Glass-x64.msi`, `Glass-x86.msi` | ProductVersion MSI |
| `GlassSettings-*.msi` в таблице заметок | `payloadVersion`: FileVersion `GlassSettings.exe` из таблицы File MSI. x64 и x86 могут различаться. ProductVersion MSI в эту ячейку не писать |
| `OpenGlassResources-x64.msi` | ProductVersion MSI |

`version.json` вручную не править. Одинаковый размер файла не доказывает, что каталог прежний: строки версий и хешей одной длины.

## Сборка установщика меняет пакеты x86

Сборка solution для `GlassSetup` идёт как Release|x86 и пересобирает зависимости Win32, включая `Glass-x86.msi` и `GlassSettings-x86.msi`. Просьба опубликовать только установщик этого не отменяет. Перед каталогом сравнить SHA-256 каждого локального MSI с уже загруженным файлом. Отличающийся подписанный MSI залить в том же релизе. Иначе установщик отклонит пакет после скачивания: `MSI SHA-256 differs from release metadata (23)`.

Хеш MSI может смениться, а FileVersion `GlassSettings.exe` — нет. В заметках число Settings меняют только вместе с `payloadVersion`.

## Подпись

Перед загрузкой у каждого нашего файла сверить отпечаток подписанта с таблицей в [docs/signing.md](../../docs/signing.md). `NotSigned` и `HashMismatch` не публиковать. `UnknownError` из-за недоверенного самоподписанного корня при том же отпечатке допустим: так описано в документе подписи. На машине автора подпись обычно даёт `Valid`.

## Каталог

Команду выполнять в текущем сеансе PowerShell. Один аргумент `-Products` в кавычках, переданный в `powershell -File`, ломает `ValidateSet`.

Полный каталог из пяти MSI и установщика, когда все эти файлы лежат в `Build\GlassSetup\Release\` и именно их байты должны остаться в релизе:

```powershell
& .\GlassSetup\scripts\New-ReleaseCatalog.ps1 -ReleaseTag v<комплект> -IncludeSetup `
  -Products platform64,platform32,settings64,settings32,openglassResources
```

`openglassResources` указывают явно: без `-Products` в каталог попадают только четыре продукта. Каталог строится после подписи и из тех файлов, которые будут загружены. Нельзя оставить в нём хеш нового установщика и хеши MSI от предыдущей публикации, если локальные MSI уже другие.

Если локально нет полного набора, а меняется часть уже выпущенного каталога:

```powershell
& .\GlassSetup\scripts\New-ReleaseCatalog.ps1 -ReleaseTag v<комплект> -IncludeSetup `
  -BaseManifest <прежний version.json> -Products <id изменившихся продуктов>
```

`-BaseManifest` сохраняет остальные записи. Список id не должен терять продукт, который остаётся в релизе.

После генерации сверить `setupPackage.sha256` с файлом `GlassSetup.exe` и `sha256` каждой записи с её MSI. Ошибка скрипта, в том числе отказ устаревшего Resources MSI, останавливает публикацию. Каталог взамен не составляют руками.

## Порядок загрузки

1. Прочитать локальные размер, время, SHA-256, подпись и версии.
2. Прочитать релиз: `gh release view <tag> --repo musicstashall/GlassPlatform --json name,tagName,assets,body`. В PowerShell выражение `--jq` передавать в одинарных кавычках.
3. Файл с тем же SHA-256 повторно не заливать. Отличающийся и проверенный по подписи — залить. Нет файла или подпись не проходит правило выше — остановиться и написать пользователю, чего не хватает.
4. Сгенерировать каталог, как в предыдущем разделе.
5. Залить изменившиеся MSI и `GlassSetup.exe`:

```powershell
gh release upload <tag> <файлы> --clobber --repo musicstashall/GlassPlatform
```

6. Обновить заметки, если изменился FileVersion установщика или `payloadVersion`. Черновик писать только в `.claude/tmp/` и удалить после `gh release edit`. Заголовок при том же комплекте не менять. Текст заметок сохранять; менять в нём только те числа, которые реально сменились. Формулировки внешних продуктов:

`OpenGlass` — используется официальный установщик из [релиза автора](https://github.com/ALTaleX531/OpenGlass/releases/latest).

`SecureUxTheme` — используется официальный установщик из [релиза автора](https://github.com/namazso/SecureUxTheme/releases/latest).

7. Залить `version.json` последним, той же командой `gh release upload --clobber`.
8. Скачать залитые файлы и `version.json` в отдельный каталог `.claude/tmp/` и сравнить SHA-256 с локальными. Совпадение размера без хеша не считать проверкой. Временные копии и черновик заметок удалить.
9. В ответе дать адрес релиза, перечислить заменённые файлы и версии, которые в таблице не изменились. Если установщик уже был открыт, его закрывают и запускают снова: работающий процесс хранит прежний снимок каталога, повтор кнопки загрузки тот снимок не обновляет.

`version.json`, загруженный раньше новых MSI, снова даёт ошибку 23. Исправление — залить байты, пересоздать каталог уже из них и залить `version.json` ещё раз последним.

## Какой набор заливать

| Просьба | Что сравнивать и заливать |
|---|---|
| Весь комплект | пять MSI, `GlassSetup.exe`, затем `version.json`. Новый тег — только если пользователь выпускает новый комплект |
| Только установщик, все MSI совпали с GitHub | `GlassSetup.exe`, затем `version.json`. Заметки: новый FileVersion |
| Установщик после сборки solution Win32 | установщик и каждый MSI, чей SHA-256 разошёлся. Обычно это оба x86. x64 и Resources не перезаливать, пока хеш тот же |
| Один продукт, например Resources | этот подписанный MSI и каталог со всеми пятью id. Остальные файлы перезаливать только при другом хеше |

Во всех строках `version.json` идёт после пакетов и установщика.
