# GlassSetup / GlassUnins: аудит и проект следующего этапа

Дата: 2026-11-04. Статус: предложение для обсуждения, не реализованный контракт.
Проверены исходники Setup, Unins, InstallSupport, WiX templates и SecureUxThemeNative.
Это статический аудит ключевых путей, не доказательство отсутствия других ошибок и не Windows integration test.

## Актуализация

Последние решения пользователя и открытые вопросы см. в **редакции 2** `product-state-contract.md`: SUT разрешён без Settings с предупреждением, все пользовательские профили + whitelist HKLM/DWM, хранение только актуального комплекта. Ранние предложения ниже при противоречии не действуют.

## Уточнения после обсуждения макета

Этот раздел имеет приоритет над первоначальными предложениями ниже; runtime-код пока не изменён.

- Пользователь утвердил независимые установку и удаление OpenGlass от Glass Platform.
- На Windows x64 Platform x86 можно устанавливать/удалять отдельно, с предупреждением о потере оформления 32-битных приложений при её отсутствии/удалении.
- Оформление B согласовано: клиентская область 1000 × 600, HTML 540 px, прогресс 4 px, footer 56 px; настоящий фон, компактные карточки и маска внутреннего списка без общей акриловой подложки.
- Отдельные уточнённые макеты: `installer-products-preview.html` и `uninstaller-products-preview.html`. Оба автономны, фон встроен data URI.
- Нижний блок предупреждений отклонён пользователем: высота списка восстановлена до 330 px. Предупреждение x86 обозначается кнопкой ⚠ на карточке, по нажатию открывается модальное пояснение. Предупреждение повторяется в итоговом плане. Это демонстрация, а не вызов engine.
- В удаляторе чекбокс «Удалить настройки» постоянно виден справа и по умолчанию снят. Он описывает текущий scope очистки: настройки GlassPlatform и OpenGlass/DWM текущего пользователя. OpenGlass независим как продукт, но явная общая очистка затрагивает и его настройки.
- В макетах выбор Platform x64 не выбирает автоматически ни OpenGlass, ни Platform x86. При удалении GlassSettings SecureUxTheme выбирается вместе с ним (сохранена текущая политика этой пары).
- Пользователь разрешил установку и сохранение GlassSettings без Glass Platform, в том числе для управления независимыми OpenGlass и SecureUxTheme. Удаление Platform x64 не должно выбирать GlassSettings/OpenGlass/Platform x86 автоматически. SecureUxTheme пока сохраняет связь с GlassSettings как интерфейсом управления. Runtime-граф и ARP-политика будут приведены к этому решению на этапе реализации.
- Интерактивная страница удаления предназначена для управления через «Изменить»/явного UI; удаление из Windows по-прежнему планируется без GUI.
- Проверены Chromium: размеры, прокрутка, видимость очистки настроек, предупреждения x86, независимость OpenGlass и x86, связь Settings/SUT и итоговый диалог. Реальные install/uninstall не выполнялись.

## 2. Риски, требующие Windows-проверки

- Setup/Unins административные, но доверие к payload не подтверждается подписью/доверенным манифестом. Проверки путей и защищённые temp не заменяют проверку источника. Это уже отмечено в README. Для постоянного cache обязательно проверить ACL и целостность перед elevated launch.
- MSI perUser + административный запуск: проверить обычный UAC и ввод учётных данных другого администратора. HKCU и применение темы должны оставаться у исходного пользователя, а не случайно у elevated account.
- Несколько MSI не образуют одну атомарную транзакцию автоматически. Unins допускает частичное удаление; восстановление оставшихся процессов не возвращает удалённые пакеты.
- Известное падение Explorer при обновлении описано в README и остаётся release blocker. Здесь оно не воспроизводилось и причина не установлена. Не смешивать изменение архитектуры MSI с заявлением об исправлении падения.
- Прямой msiexec /x обходит helper. NoRemove не является защитой от CLI. Если безопасность удаления SUT зависит от стандартного стиля, нужен fail-safe guard в MSI или отдельное согласованное ограничение standalone removal.

## 3. Предлагаемое разделение ответственности SecureUxTheme

### Три независимых состояния

1. Payload доступен: проверенный SecureUxTheme.msi находится в защищённом cache/каталоге установки.
2. MSI установлен: Windows Installer владеет System32/SysWOW64, компонентами и машинной регистрацией.
3. Визуальный стиль: пользовательский профиль и текущая сессия, управляемые GlassSettings/helper.

Хранение MSI не считать установленным/включённым SecureUxTheme. «Подготовлен», «Установлен», «Ожидает перезагрузки», «Конфликт» — разные состояния.

### Установка/включение

- Проверить архитектуру, издателя/доверенный hash, версию, ProductCode/UpgradeCode, отсутствие чужой установки и конкурентной операции.
- Атомарно опубликовать полный MSI в защищённом каталоге. Простой copy из доступного для записи пользователю места перед elevated execution недостаточен.
- Контроллер, не custom action родительского MSI, запускает SecureUxTheme.msi с UI none и REBOOT=ReallySuppress, сохраняет подробный MSI log и 3010.
- Файлы и регистрацию делает только SUT MSI. Не вызывать вложенную установку MSI из MSI custom action.
- GlassSettings больше не копирует/удаляет эти файлы и не создаёт cleanup.cmd/task для них.

### Отключение/удаление

- Helper в исходной пользовательской сессии переключает на штатный стиль и подтверждает результат.
- При невозможности безопасно переключить стиль — ошибка без удаления SUT по умолчанию. Продолжение до перезагрузки требует отдельно спроектированного безопасного состояния; не считать это уже решённым.
- После этого контроллер удаляет зарегистрированный продукт по ProductCode в нужном install context, UI none, reboot suppressed.
- MSI снимает только принадлежащие ему регистрацию и файлы; заблокированные файлы остаются под учётом Windows Installer до перезагрузки.
- Helper и оболочка сохраняются до завершения операции; не удалять DLL helper раньше выполнения всех его функций.
- Нужна отдельная миграция legacy manually managed файлов: не присваивать MSI чужой SecureUxTheme, не удалять чужие IFEO/verifier tokens. Проверить shared registry values и rollback upstream MSI.

Нельзя пока гарантировать, что имеющийся/сторонний MSI корректно реализует эти обязанности: требуется аудит его WXS, custom actions, идентификаторов, лицензии и x86 proxy на x64. Нынешний template в этом репозитории — только payload MSI и для этой схемы недостаточен.

## 4. Управление через «Установленные программы»

### Термины зависимости

«Зависимость» — продукт, который требуется другому установленному продукту. «Зависимый продукт» — тот, который сам использует другой. Кнопку безопаснее блокировать у используемой зависимости, а не у любого продукта с prerequisites.

Предлагаемое начальное дерево (сохранить текущую политику до решения об отвязке продуктов):

```
GlassSettings ──requires──> native Glass Platform
OpenGlass    ──requires──> native Glass Platform (нынешняя политика; необходимость обсудить)
Platform x86 ─requires──> native x64 (нынешняя политика на x64; необходимость обсудить)
SecureUxTheme──requires──> GlassSettings (владение/управление, не техническая загрузка DLL)
```

Это не утверждение о технических требованиях upstream OpenGlass/SUT. Если OpenGlass должен быть независим, меняем граф осознанно, а не автоматически удаляем его с core.

### ARP-контракт

| Действие | Предлагаемая команда/поведение |
|---|---|
| Изменить | `GlassSetup.exe --modify --product <stable-id>` из постоянного защищённого cache. Фокус на продукте, показ всего дерева. |
| Удалить | `GlassUnins.exe --remove --product <stable-id> --silent`. Никакого WebView/нативного мастера. |
| QuietUninstallString | Та же headless команда. UAC при необходимости остаётся: «без GUI» не означает обход elevation. |
| Используемая зависимость | NoRemove=1; при необходимости отсутствие UninstallString проверить на Windows. Engine повторно запрещает удаление, даже если вызван вручную. |
| Удаление уже отсутствующего продукта | Идемпотентный успех после проверки identity/context; неизвестный stable-id — ошибка. |
| Ошибка/занято/перезагрузка | Ненулевой код ошибки / 1618 / 3010, журнал и машинно-читаемый result. Без скрытого успешного каскада. |

`NoModify=0`/отсутствие NoModify и `ModifyPath` дают контракт классической панели «Программы и компоненты». Windows 10/11 Settings могут показывать «Изменить» иначе или не показывать отдельную кнопку для конкретного типа регистрации. Это нужно проверить на целевых сборках; обещать идентичную кнопку везде нельзя. Запасной вход — «Управление продуктами» в GlassSettings/меню Пуск.

Рекомендую собственные видимые non-MSI ARP-записи со стабильными ID и скрытые MSI (`ARPSYSTEMCOMPONENT=1`), а не ручное удаление WindowsInstaller у MSI-записи. После каждой операции пересчитывать reverse dependencies и все NoRemove. При неуспехе пересчитывать по факту, а не по плану.

В modify UI снятый checkbox НЕ должен вдруг означать удаление: текущее значение — «оставить установленное». Для управления использовать явные действия «Оставить / Обновить / Восстановить / Удалить» и финальную сводку. В свежей установке достаточно checkbox «Установить».

## 5. Постоянная оболочка в ProgramData

Полноценный bootstrapper реализуем. Кэш — часть продукта с жизненным циклом, а не произвольная копия setup.exe.

Предлагаемый путь: `%ProgramData%\Packages\GlassPlatform\<bundle-version>\` (C: не хардкодить). Сам `Packages` не считать принадлежащим Glass: никогда не чистить общий каталог.

Содержимое: подписанные Setup/Unins/helper и ресурсы, manifest с версиями/хэшами/архитектурами, полные MSI с media, transaction journal и указатель на последнюю исправную оболочку. Windows Installer LocalPackage — не гарантия наличия полного источника для repair.

- SYSTEM/Administrators могут писать, Users — только читать/выполнять. Проверять владельца, ACL, reparse points; hash list в изменяемом каталоге не корень доверия.
- Cache принадлежит отдельному controller/bundle, не удаляемому раньше потребителей. Не использовать его одновременно как произвольно очищаемый download cache.
- Новую версию публиковать рядом, проверять, затем переключать активную; оставить предыдущую до успешного завершения и rollback window.
- Разделить unelevated UI и elevated worker с узким протоколом и проверкой клиента/плана. Применение темы — в пользовательской сессии.
- Нужен machine-wide lock для операций; текущий Local mutex не должен стать единственной синхронизацией машинного cache между сессиями.
- Последнее удаление: защищённая временная копия worker, удалить продукты, ARP и затем только принадлежащие Glass версии cache; остатки reboot/pending имеют явный учёт.
- Без сети доступны modify/repair/remove для закэшированных версий. Missing/corrupt cache — диагностируемая ошибка/восстановление из доверенного источника, не запуск найденного EXE.

Варианты: развивать текущий custom bootstrapper (меньше изменений UI, больше собственного кода lifecycle/rollback) либо WiX Burn как владелец chain/cache/elevation и custom BA для UI (существенная миграция; автоматическое решение user-theme/dependency semantics он не даёт). Рекомендация: сначала общий planner/контракт worker, затем отдельный прототип Burn, не полный rewrite сразу.

## 7. Макеты и проверки этого этапа

`product-selection-concepts.html` — три независимых визуальных подхода в одном автономном файле: A «Список + план» (рекомендуется), B «Каталог карточек», C «Дерево зависимостей».
