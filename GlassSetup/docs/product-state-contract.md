## Дополнительное согласование

Подробный актуальный алгоритм и проверка присланного экспорта: `cache-profile-maintenance-contract.md`.

- Staging/rollback временно разрешены; постоянная история комплектов запрещена.
- Source оставленной старой версии сохраняется только при реальной необходимости обслуживания отличающейся версии; после update/remove автоматически удаляется, когда больше нет installed/transaction/reboot/recovery references. Полный прежний bundle для одного старого MSI не хранить.
- Preflight всех профилей до очистки принят; обнаруженный отказ — не начинать, поздний отказ — частичный результат.
- Не завершать чужие сеансы; при невозможности безопасного изменения предложить выйти и повторить.
- Сброс custom visual style при удалении SUT — обязательная отдельная операция и не зависит от checkbox общей очистки. Незагруженные профили не монтируются.
- Трактовка запрета тихого удаления GlassSettings при установленном SUT подтверждена пользователем; явный UI-план допускает раздельное удаление.
- Экспорт HKLM/DWM: 228 значений, 223 session activity IDs, ни одного совпадения с текущим whitelist OpenGlass. Удаление всего DWM не допускается; точное происхождение всех значений не проверено чистым Windows baseline.

## Принятые правила

| Продукт / действие | Послеоперационное состояние и UI |
|---|---|
| Platform x64 отсутствует или удаляется | Независимый выбор; ⚠ о недоступности оформления 64-битных приложений, карточка жёлтая |
| Platform x86 на Windows x64 отсутствует или удаляется | Независимый выбор; ⚠ о недоступности оформления 32-битных приложений, карточка жёлтая |
| GlassSettings отсутствует или удаляется | Выбор разрешён; ⚠ о ручном редактировании реестра и управлении службами/задачами, карточка жёлтая |
| SecureUxTheme устанавливается/остаётся активным без GlassSettings | Разрешено на ответственность пользователя, ⚠ на карточке SecureUxTheme: ручной контроль стилей и перезапуска системы. Не добавлять Settings автоматически |
| GlassSettings удаляется, SUT сохраняется | SUT не выбирать и не блокировать автоматически; предупреждение и явный UI-план |
| SUT выбран для удаления | Штатный стиль через helper, затем MSI; неудача safe-style preflight по-прежнему останавливает небезопасное удаление. Наличие отдельного helper в постоянной оболочке необходимо даже без Settings |
| OpenGlass | Независимые установка/удаление, без каскада от Platform/Settings |
| Первоначальный выбор на x64 | Platform x64 + Platform x86 + GlassSettings + OpenGlass; SecureUxTheme не выбран |
| «Выбрать всё» | Доступные продукты; не очистка настроек/сертификат. Кнопка выровнена по правому краю панели плана |
| Счётчик | «Выбрано продуктов: N из M» над списком, тот же счётчик в footer; подсказка о скрытых ниже/выше продуктах |
| Установщик: снятая отметка установленного продукта | Keep, а не удаление. Предупреждение об отсутствии только если продукт действительно будет отсутствовать |
| Выделение | Каждая карточка с предупреждением жёлтая, ⚠ под её иконкой; прежнее полупрозрачное окно без нижних кнопок |
| Настройки | Один checkbox для всех локальных пользовательских профилей и относящихся к продуктам общих HKLM/DWM значений. По умолчанию выключен; сбрасывает и настройки сохраняемых продуктов |
| Cache | Только последний успешно установленный комплект; бессрочное хранение истории версий отклонено |

Headless remove Settings при установленном SUT: пользователь подтвердил запрет тихого удаления и право на раздельное удаление через явный UI-план. Поэтому трактуем как **ограничение entry point**, не жёсткую зависимость SUT → Settings: ARP remove не открывает GUI, возвращает отказ с направлением в «Изменить», а UI разрешает сохранить SUT после предупреждения. Если подразумевалось разрешить и тихое удаление с сохранением SUT, это нужно уточнить отдельно. Защитное переключение стиля перед удалением самого SUT не отменено предупреждением.

## Cache

Предлагаем steady-state layout `%ProgramData%\Packages\GlassPlatform\Current\` с проверенной оболочкой, manifest и полными MSI только актуального комплекта. Путь ARP стабилен. Разные компоненты/архитектуры в Current не являются историей версий. Отказ от обновления одного продукта не должен лишать его доступного repair source: текущий комплект должен содержать источники фактически оставленных версий либо явно поддерживать их восстановление.

Для обновления допускается временный Staging новой версии и rollback-данные прежней. Это не постоянная история: после успеха или закрытия rollback-window они удаляются; при ошибке сохраняются до recovery с явным статусом. Постоянная история комплектов не хранится.

## Очистка всех профилей: реализуемость и границы

Да, HKCU каждого профиля можно обслужить административным worker, но HKCU самого elevated процесса не представляет всех пользователей.

1. Перечислить реальные профили по ProfileList и SID, валидировать пути/владельцев. Не обходить произвольные каталоги Users. Профили без NTUSER.DAT отметить как неинициализированные, не создавать hive.
2. Загруженный профиль: работать с `HKEY_USERS\<SID>`, не закрывать и не выгружать системный mount. Незагруженный профиль не монтировать: отсутствие ключа — пропуск с предупреждением, не загрузка NTUSER.DAT.
3. Не трогать .DEFAULT, Default User, SYSTEM/LocalService/NetworkService, специальные системные профили или чужие файлы. Наличие SID в SAM без созданного профиля не означает hive для очистки.
4. Обработать оба применимых registry view; HKLM обработать один раз, не на каждого пользователя.
5. В DWM удалять **только whitelist параметров OpenGlass** из SettingsCatalog/RegistrySanity, а не раздел DWM целиком, не базовые Colorization/EnableTransparency Windows. Не удалять регистрацию MSI, пути установки и задачи при операции очистки настроек.
6. Активные Settings и процессы других сеансов могут записать параметры обратно. Нельзя гарантировать «все очищено» без координации сеансов. Не завершать чужие сеансы автоматически.
7. Недоступный, занятый или повреждённый hive — явный частичный результат по SID, не успех и не молчаливый пропуск. Сначала проверить доступность всех профилей, а при ошибке не начинать очистку; гонка между preflight и commit всё равно требует журнала и отчёта.
8. Очистка необратима без отдельной backup-политики. Продукты могли быть успешно удалены, а очистка части профилей — не выполнена; результат обязан разделять эти стадии. По умолчанию не чистить настройки после неуспешного выбранного удаления.
