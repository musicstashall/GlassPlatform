# Delphi VCL: начальная поддержка

## Наблюдения по журналу DelphiControlsSample (Full, x64)

* `TGroupBox` и `TTabSheet` классифицировались как DelphiContainer, но ветки
  attach для них не было. `TPageControl`, `TToolBar`, `TTrackBar`,
  `TScrollBar`, `TDateTimePicker` и `TStaticText` попадали в Unknown.
* VCL вызывает из EXE `DrawThemeBackground` (в том числе TABP_PANE для
  `TTabSheet` и BP_GROUPBOX для `TGroupBox`) и `DrawThemeTextEx` для
  заголовков групп и безоконных `TLabel`. Встречаются также `ExtTextOutW`,
  `PatBlt`, `FillRect`, `BitBlt`, в том числе для memory-DC и изображений;
  превращать эти вызовы в прозрачные без различения назначения нельзя.
* В конце журнала зафиксирован `0xC0000005` в EXE при завершении. Один адрес
  не позволяет определить причину и связь с Glass или пробником: необходим
  указанный в журнале дамп и стек. Считать это исправленным нельзя.

## Сделано

Контейнеры подключаются к обычному root-пути при Full и разрешённом backdrop;
перечисленные обёртки штатных контролов направляются в их существующие
провайдеры. На `TGroupBox`, `TTabSheet`, `TPanel`, `TScrollBox` дополнительно
включается в BeginPaint/GetDC сессионный IAT `DrawThemeTextEx` модуля EXE.
Обработка ограничена совпадающим HWND оконного DC и хозяином сессии текущего
потока, пропускает измерение и callback, сохраняет DTTOPTS и при ошибке
использует оригинал. `TPageControl` не меняет общую кисть класса табов.
Исходный диагностический зонд не включается.

## Ограничения и проверка на Windows

Это не полная поддержка VCL: произвольные потомки, динамический вызов через
GetProcAddress/пакеты BPL, memory-DC, `WM_PRINTCLIENT`, отрисовка фона
`DrawThemeBackground` самим VCL, owner-draw и нестандартные таблицы/контролы
требуют отдельного конвейера и проверки. IATRegistry поддерживает цепочку
различных detour через trampoline; порядок перехватов и охват отдельных
модулей всё равно требуют проверки. Не предполагать, что все вызовы из журнала
перехватываются новым хуком.

Собрать x64 Debug на Windows и проверить sample в Full, PopupOnly и при
запрещённом backdrop: форму, вложенные группы и страницы, подписи с/без HWND,
изменение размера, переключение страниц, активное/неактивное окно, светлую и
тёмную темы, нетематический режим, DPI, повторное создание и закрытие окон,
а также включение/выключение платформы. Проверить, что текст и изображения не
исчезают, не затрагиваются другие приложения/окна и после выгрузки нет зависших
субклассов; сверить журнал attach и сессий. Сравнить снимки с Glass OFF. Для
аварии при закрытии нужен отдельный разбор дампа. Portable source-contract
проверка: `python3 WndCompat/tests/delphi_pipeline_contract.py` — она не заменяет
сборку и визуальные/жизненные тесты.

## Журнал повторной проверки (Full, x64, light)

`TPageControl` маркируется как TabControl, но его BeginPaint в наблюдаемом
запуске вызван из EXE; при этом для `TTabControl` зафиксирован вызов табового
DrawThemeBackground из comctl32, когда BeginPaint тоже шёл из comctl32.
Первоначальная табовая сессия включала IAT только модуля BeginPaint. Теперь для
двух VCL-классов `TPageControl`/`TTabControl` дополнительно включаются известные
экземпляры comctl32, без повторной установки на caller, с симметричным снятием
из сохранённой сессии. Это исправление предполагаемого пропуска, не подтверждение
фактического пути отрисовки TPageControl: новый журнал без зонда не показывает
его вызовы DrawThemeBackground. Проверить отрисовку и `TabHooks` в Windows;
если сессия есть, но перехвата нет, проверить динамические вызовы и конфликты IAT.

Для `TMemo`, `TListBox`, `TTreeView`, `TResTreeView`, `TListView`,
`TSystemListView` и `TRichEdit` в журнале видна классификация/attach; для
ListView и TreeView видны отдельные сессии/текстовые хуки. Это не доказывает,
какой вызов перекрывает фон. `TRadioGroup`, `TRelativePanel`, `TButtonGroup`,
`TCategoryButtons`, `TNumberBox`, `THotKey`, `TControlBar` и `TShownValueList`
идут через Unknown → Root_Attach, что само по себе не обеспечивает их VCL paint.
Для поиска источников фона, текста и memory-DC нужны адресные API-трассы.

В конце этого запуска снова зарегистрирован `0xC0000005` в EXE (тот же RVA,
что в первом журнале), создан минидамп. Стек и причинная связь с Glass неизвестны.

## API Monitor: повторная трасса отрисовки

Текстовый экспорт охватывает примерно 16:22:42–16:22:52, отдельный запуск
относительно журнала Glass 16:02. В одном BeginPaint, инициированном
COMCTL32, для того же оконного DC наблюдаются `SetBkColor(0xFFFFFF)`,
`CreateSolidBrush(0xFFFFFF)`, `FillRect` и `DrawTextW("TListView")`. Это
указывает на белую заливку в пути рисования с таким текстом, но не доказывает
её размер, роль или то, что данный HWND — именно VCL TListView: экспорт не
содержит разрешённых RECT, имени класса HWND и стека вызова. В другом paint
COMCTL32 создаёт compatible bitmap/DC, рисует на нём и копирует `BitBlt`.
HDC повторно используются для разных окон, поэтому сопоставлять их вне
отдельной пары BeginPaint/EndPaint или GetDC/ReleaseDC нельзя.

В `ListViewHooks.cpp` уже есть сессионный IAT `COMCTL32!FillRect` с
преобразованием кисти COLOR_WINDOW в BLACKNESS. По уточнению пользователя,
трасса API Monitor записана **без запущенной Glass**; она показывает исходный
путь рисования, но не поведение Glass и не доказывает, что Glass пропустила
данный вызов. Не следует обобщать эту заливку на все белые кисти или отключать
фоны элементов/выделения.

Для `TMemo` по этому экспорту также нельзя надёжно выделить изменение фокуса
или связать конкретные вызовы с классом HWND. `DrawThemeBackground` в выборке
не наблюдается, но это не доказывает отсутствие вызовов без информации о
фильтрах. Предлагавшаяся совместная запись LogViewer и API Monitor оказалась
не нейтральной: см. результаты ниже. Для TPageControl также требуется изучить
DrawThemeBackground/Ex и уточнить версию сборки Glass.

## Совместный запуск Glass и API Monitor

В следующем запуске Glass активна, API Monitor подключён после старта
приложения. Нативный файл сеанса `Delphi.apmx64` содержит данные API Monitor;
его бинарные записи здесь не декодировались, выводы основаны на текстовом
экспорте и LogViewer. Журнал Glass начинается уже после запуска, поэтому
классы ранее созданных HWND в нём не всегда видны.

API Monitor влияет на определение вызывающего модуля: после подключения Glass
фиксирует `BeginPaint` для ListView, Edit, Tab и Button с caller
`apimonitor-drv-x64.sys`; в текстовом API-экспорте для тех же HWND вызов
приписан COMCTL32. До подключения монитора виден caller COMCTL32. Например,
у ListView при 16:32:06.092 совпадают HWND и время BeginPaint, но модули
различаются. Это важно: ListView включает ряд IAT-хуков только при caller
`g_comctl32New` / `g_comctl32Legacy`. Следовательно, одновременная запись
может изменять работу конвейера, а не только наблюдать его. По ней нельзя
выводить, что именно происходит без монитора; одновременно нельзя считать,
что все остальные перехваты обязательно не работают.

На ListView-сессии в этом запуске COMCTL32 записал чёрную кисть в FillRect,
а не белую из исходного запуска без Glass. Журнал сам по себе не доказывает
альфа-состояние поверхности после операции и причину видимого фона. У одного
Edit-HWND видна FillRect с кистью, возвращённой через CTLCOLOR, но здесь нет
подтверждённого имени класса, содержимого кисти/RECT или момента потери фокуса;
приписывать этот вызов TMemo и конкретному дефекту нельзя.

Строки Tab BeginPaint в присланном журнале не содержат добавленные в c91023a
поля `vclComctlNew` / `vclComctlLegacy`; это указывает на сборку без данной
диагностики. Проверить точный коммит и использовать новую сборку. Для
дальнейшей диагностики предпочтительны LogViewer отдельно, без API Monitor,
и точечные встроенные probes; API Monitor запускать как отдельный контроль,
не считать его прозрачным для IAT/Detours. Авария `0xC0000005` в EXE при
закрытии повторилась; нужен дамп и анализ стека, а не предположения по адресу.

## Повторный тест без внешнего монитора

Пользователь очистил LogViewer после запуска и затем последовательно переключал
вкладки до закрытия. В строках Tab BeginPaint есть `vclComctlNew`; следом
наблюдаются вызовы `TabHooks::Overall_MyDrawThemeBg` из COMCTL32 с part 9,
5, 6 и 7. Значит, путь IAT на COMCTL32 действительно достигнут; это не
подтверждает визуальное качество или фон VCL `TTabSheet`. В сессиях ListView
caller — COMCTL32, текст `TListView` / `TSystemListView` доходит до Glass;
по этим записям нельзя установить альфа фона. Из-за очистки до переключения
для заранее созданных HWND нет строк attach/class. Конкретный переход фокуса
TMemo тестом не отмечался. В конце опять зарегистрирован `0xC0000005` в EXE;
минидамп необходим для определения причины.

Для следующей проверки добавлены **только Debug-логи в уже существующих
обработчиках**, без нового детура или IAT: `[WndCompat][DelphiMemo]` выводит
CTLCOLOR, фокус, исходную и результирующую кисти для TMemo;
`[GlassCore][DelphiListView]` — предыдущие цвета ListView, флаг первичной
очистки и вызовы существующего IAT FillRect для TListView/TSystemListView.
Ограничение — 16 записей в секунду на поток для каждого вида; текст контрола
не пишется.
Отсутствие записи FillRect не доказывает отсутствие заливки другими путями
или сессионного IAT. Проверять отдельно, без API Monitor и DebugDetour,
открыть нужную страницу, затем очистить LogViewer и перевести фокус в TMemo
и из него; для ListView принудить перерисовку/прокрутку и записать лог и
скриншот. Дополнительно собрать лог с запуска, если потребуется сопоставить
HWND с классами.

## Тест фокуса и скрытия/показа

В логе после очистки TMemo `0x908F6`: WM_CTLCOLOREDIT (0x133), и до,
и после получения фокуса VCL возвращает белую сплошную кисть и белый bk;
root подставляет чёрную кисть и bk=0. Это не объясняет само по себе
исчезновение текста при фокусе. `EnsureEditBuffer` фиксирует multiline
buffer, dual pass и наличие bitmap-снимка (не успешность его копирования).
В фокусном WM_PAINT вложен GetDC, за ним создание буфера, ReleaseDC и
EndPaint. Текст/альфа/результат композита в этом журнале не видны.

Обнаружена независимая ошибка жизненного цикла: начало любого Edit GetDC
безусловно очищало накопленные ETO_OPAQUE-прямоугольники и сбрасывало fallback,
включая случай вложенного GetDC во время paint или другого GetDC. Теперь сброс
производится только в начале внешней GetDC-сессии без paint. По текущему логу
нельзя доказать, что в момент вложенного вызова уже были накопленные области,
или что именно это вызывает описанный дефект TMemo. Добавлены ограниченные
Debug-записи маршрута ExtTextOut и flush для TMemo (число символов и параметры,
без текста); они не диагностируют все API отрисовки и итоговую альфу.

В 07:46:33.257 для единственной наблюдаемой сессии VCL ListView `0x50570`
получены bk=0, textBk=0, flipped=0, first=0. Две перехваченные заливки чёрной
кистью на оконных DC имеют прямоугольники [1,1,189,87] и [0,0,92,16]; затем
наблюдается текст `TSystemListView`. Диагностика проверяет класс TListView или
TSystemListView, но старая запись не различает их: текст не доказательство
класса HWND. Чёрный RGB сам по себе не подтверждает значение альфы, площадь
клиента или отсутствие последующих заливок в других модулях. Скрытие/показ —
не создание HWND; first=0 здесь ожидаем для уже обработанного окна. В Debug
расширен Begin логом фактического класса и client rect, добавлен PostBegin
с rcPaint/fErase/needBlackout; новых IAT/Detours не добавляли.

Проверка Windows: фокус и потеря фокуса TMemo (в том числе выделение текста),
скрытие/показ **обоих** классов ListView, прокрутка, изменение размера и
повторное создание. Прислать скриншот с названием контрола и Debug-лог без
зонда и API Monitor. Изменение управления буфером — потенциальный фикс, а не
подтверждённое решение визуальных проблем; скомпонованный результат и фон
нужно проверять отдельно.

## Тест 4: текст TMemo и два класса ListView

Пользователь сообщает: текст TMemo исчезает при получении и потере фокуса,
но при выделении снова виден, и кисть выделения имеет альфу. Для `0x1E05CA`
лог показывает в WM_PAINT обычный чёрный текст `textColor=0`, black bk и
сессионный путь; при выделении в GetDC виден также белый текст `0xFFFFFF`
с цветным `bk=0xD77800`. Логи до рендера не доказывают состояние итоговой
альфы. Предыдущая защита накопленных ETO_OPAQUE областей не устранила симптом.

Гипотеза: обычный чёрный текст теряет альфу при композиции через
CreateCompatibleBitmap, поскольку совместимая bitmap не гарантирует хранение
альфы. Эксперимент для класса `TMemo`: 32bpp DIB для снимка и compose во
время буферизованного WM_PAINT; при ошибке выделения — прежний bitmap.
Прямой GetDC-путь не меняется. В Debug также пишется только суммарное число
ненулевых alpha-пикселей текстового DIB и compose DIB, максимальная alpha,
успех blend/copy и tblend, не содержимое текста/изображения. На больших
буферах (>4 млн пикселей) статистика не рассчитывается. Данные о DIB не
доказывают, что alpha дошла до итогового окна; BitBlt с оконного DC и обратно
зависит от формата целевой поверхности. Требуется визуальная проверка и
исследование GetDC-пути, если дефект сохранится.

Подтверждены классы обоих списков: `TSystemListView` `0xA07AE` клиент
186×84 и `TListView` `0x170BB2` клиент 166×84. При первом paint цвета до
переключения белые, затем становятся нулевыми; post-BeginPaint очищает
соответственно весь клиент и область под заголовком. После скрытия/показа
первичная очистка не повторяется. В дальнейшем в обоих случаях виден чёрный
solid FillRect на оконном DC с прямоугольником примерно всего клиента и
отдельные маленькие заливки элементов. В этой версии экспериментально только полноразмерный
чёрный FillRect на оконном DC этих двух классов заменялся на BLACKNESS;
в следующей версии эксперимент снят, см. ниже. Это не доказывает, что обычная кисть давала непрозрачную
альфу или что вызов отвечает за видимый фон. Мелкие области, memory DC,
другие классы и цвета не меняются. Больше никаких перехватов не добавлено.

При закрытии снова `0xC0000005` в EXE по тому же IP, дамп
`DelphiControlsSample_Win64.exe.24940.dmp`; имеются повторные предупреждения
несимметричного отключения theme hooks. Требуется сам дамп/стек и сравнение
с Glass OFF; связь с изменениями и друг с другом не доказана.

Windows: собрать x64 Debug, без зонда/API Monitor проверить TMemo с фокусом,
без фокуса, при частичном/полном выделении, прокрутке, включая Memo с цветным
фоном; оба ListView при первоначальном открытии и скрытии/показе, прокрутке и
изменении размеров. Проверить обычные Edit/ListView и Glass OFF. Нужны лог и
скриншоты; диагностика и эксперименты не являются подтверждённым исправлением.

## Разбор дампа пользователем и тест 5

По предоставленному пользователем разбору cdb, два дампа 21652/24940 имеют
`0xC0000005` (и последующий `0xC000041D`) в
`DelphiControlsSample_Win64.exe+0x3DD029`: `TApplication.WndProc` читает
`Self+0x160` на освобождённой странице во время `WM_ACTIVATEAPP` (активация).
Автоматическая раскрутка Delphi непригодна; пользователь восстановил стек по
прологам/слотам. Присутствующий `RootSubclassProcShared` передаёт сообщение
через `DefSubclassProc`, не обрабатывая его. На основании одного стека нельзя
сказать, кто освободил объект, почему остался жив HWND, или вызвала ли это
платформа; оригиналы дампов в этом рабочем пространстве не предоставлены.

Анализ текущего кода: Root_Attach устанавливает SetWindowSubclass, а для
GA_ROOT дополнительно меняет кисть класса и запускает root hooks/SWCA/DWM.
WM_NCDESTROY до DefSubclassProc вызывает RootHandleRootAttachedWndNcDestroy:
убирает записи реестров и вызывает OnRootHooksDetach; RootSubclass не вызывает
DestroyWindow и не владеет временем жизни VCL объекта или HWND. Удаление записи
при полученном WM_NCDESTROY не объясняет, почему сообщение пришло до него.
comctl32 отвечает за цепочку subclass при уничтожении окна. В новом логе
`0x14060A` с классом `TApplication` был классифицирован root и получил весь
этот attach; до нового исключения нет строки WM_NCDESTROY для него. Сам лог не
доказывает, что это именно HWND из предыдущего дампа или почему оно ещё жило.
После уничтожения формы в текущем логе виден attach диалога #32770, затем
исключение по IP `0x10AD029` в EXE; событие или диалог не доказаны как причина.

В этой версии экспериментально исключено служебное окно **точного класса**
`TApplication` из классификации и добавлен guard в Root_Attach для прямых
вызовов в обход классификатора. Не перехватываем WM_ACTIVATEAPP, не
уничтожаем HWND, не подменяем WndProc и не пропускаем чужие сообщения; остальные
VCL формы/контролы не исключены. Это убирает ненужное вмешательство в служебное
окно, но не исправляет автоматически освобождение VCL-объекта и не доказывает
причину краша. Новый запуск обязателен; если авария остаётся, сравнить стек и
дамп с Glass OFF (без платформы), определить HWND сообщения и время уничтожения
TApplication, отдельно проверив, доходит ли до его WM_NCDESTROY.

В новом логе WM_PAINT для TMemo содержит `inkAlphaCount=389`, `inkAlphaMax=255`,

## Тест 10: время жизни DC в TMemo

Пользователь подтвердил дочерний Edit TComboBox; в TMemo на третьей странице
текст виден при первом показе, исчезает после фокуса и появляется при начале

Compose `alphaCount=1365`, Copy `ok=1`. Эти величины не измеряют итоговый
альфа-канал окна.

При фокусе в 09:47:07.890 onBegin Edit уже активен, но оригинальный BeginPaint
ещё не вернул клиентский HDC. Вложенный GetDCEx с `DCX_WINDOW` отдаёт оконный
DC с пустым clip; текстовый hook создаёт на его основе буфер (`fromGetDC=0`).
Этот DC освобождён до возврата BeginPaint в 09:47:07.899. Клиентский paint
использует другой DC, но буфер сохраняет исходный `screenDC`; Flush в EndPaint
получает nonzero ink. В этот раз записаны Flush и DeleteDC, но нет Compose/Copy;
такое возможно на fallback или при лимите DEBUG, а само отсутствие записей не
доказывает конкретный сбой GDI. Аналогичный порядок наблюдался и при других
перерисовках. Отдельный GetDC/ReleaseDC после EndPaint и другие источники
фоновой отрисовки не исключены. Выбор уже освобождённого целевого DC — сильная
гипотеза для исчезновения текста, не подтверждённая визуальным испытанием.

Эксперимент ограничен точным классом TMemo при активном Edit BeginPaint:
post-BeginPaint callback сохраняет действительный клиентский HDC, не меняя
фон и `fErase`. Только текст именно в этот HDC может создать или использовать
сессионный буфер; ближайшая запись этого HDC в стеке диспетчера также должна
быть Paint данного HWND, а не вложенный GetDC. До возврата BeginPaint, для
прочих DC и для неподходящего уже существующего буфера вызов направляется в
оригинальный ExtTextOut с неизменными параметрами. Обычные отдельные
GetDC/ReleaseDC без paint-сессии и другие классы остаются на прежнем пути.
Проверка не делает вывод о принадлежности произвольного memory DC по контексту;
при ином buffered-пути TMemo текст в таком DC пока проходит через оригинал,
что может потребовать отдельной проверки. Нет гарантии для обходящих диспетчер
вызовов или иных вложенных paint-сценариев.

DEBUG `PaintBind`, `BufferTarget`, `NonPaintPass`, `ComposeFallback` позволяют
сопоставить HDC и fallback без содержимого текста; к ним применяются прежние
лимиты. Для нового прогона собрать x64 Debug на Windows и без общего зонда
проверить первый показ, фокус/выход, выделение мышью и клавиатурой, набор,
прокрутку и resize TMemo, а также регрессию ComboBox и TShownValueList.
Если дефект останется, прислать Glass-лог с этими моментами и скриншоты;
контрольные точки — `PaintBind` и совпадающие `BufferTarget screenDc/paintDc`,
затем Flush, Compose/Copy или ComposeFallback. Windows-сборка и визуальная
проверка этого эксперимента в Arena не выполнялись.

  подтверждённым цветом alpha 255. В оконный DC BitBlt ограничен оригинальным

  сессионный буфер или не было подтверждающего text rect, этот шаг не сработает.

`confirmed` и `primed`, и target compose/fallback. Визуальное исправление
полосы пока не подтверждено. Проверить на Windows выделение/прокрутку вниз и
вверх, деактивацию, resize и перерисовку, сравнить с тем же TMemo без Glass;
обязательно также проверить прозрачный обычный TMemo и цветной редактируемый,
частичное выделение и смену цвета. При регрессии/полосе полезен короткий лог с
этой диагностикой. Эксперимент может не сработать, если дефект вызван поздним
рисованием или прокруткой вне BeginPaint; глобальный зонд не включать.

## Тест 14: owner-draw TBitBtn

Пользователь подтвердил работу TLabeledEdit, TButtonedEdit, TMaskEdit и
введённого текста TSearchBox; задачи по ним закрыты. В `LogViewr-14` для
TBitBtn (`style=0x5401000B`, `BS_OWNERDRAW`) наблюдается `WM_DRAWITEM` на
родительском HWND. При обычной перерисовке HDC в DRAWITEMSTRUCT является
memory DC (`WindowFromDC == NULL`), созданным совместимым с оконным DC; при
обработке фокуса в логе встречается непосредственно оконный DC. Пустая
BeginPaint-сессия Button поэтому не означает отсутствия отрисовки.

По анализу пользователя, VCL рисует кнопку в WM_DRAWITEM из EXE: копирует фон
через DrawThemeParentBackground, рисует часть темы Button/BP_PUSHBUTTON через
DrawThemeBackground и текст через DrawThemeTextEx. Эти конкретные вызовы в
`LogViewr-14` не трассировались: пассивный лог подтверждает сообщение/HDC, а
не отдельные API или содержимое буфера.

Эксперимент: parent с Root subclass оборачивает исходный DefSubclassProc в
сессию только для дочернего exact TBitBtn/ODT_BUTTON/BS_OWNERDRAW, с Full,
Button mark и разрешённым backdrop. HWND, rect и точный HDC берутся из
DRAWITEMSTRUCT; текущая сессия хранится по потоку и снимается после вызова,
включая вложенные сообщения. На время сессии в IAT EXE включены только
DrawThemeParentBackground, DrawThemeBackground и DrawThemeTextEx. Базовая
очистка ограничена этим HDC и rect; первоначально для темы
Button/BP_PUSHBUTTON и полного rcItem вызывался существующий Button alpha
renderer, а текст рисовался через
существующий DrawThemeContent с DTT_COMPOSITED. Измерение, callback, чужой HDC
или другая часть темы отдаются оригиналу. Сохранены состояния, rect и VCL
обработка; кнопка и её глиф не заменяются целиком. Для exact TBitBtn выключен
существующий Button BitBlt-перехват: его глиф не обязан выставлять
BS_ICON/BS_BITMAP, даже если присутствует изображение. Остальные кнопки и их
фильтры не меняются.

IAT в процессе общая, и этот эксперимент может пересекаться с другими IAT
детурами на те же API; это не диагностический DebugDetour. При пакетной сборке
VCL вызовы могут идти из BPL, а не EXE; parent может не иметь Root subclass;
внутри VCL возможен иной HDC или класс/part темы. Ни один из этих случаев не
считается автоматически поддержанным. Буферный comctl32 и последующая копия
также могут менять видимый результат. Отрисовка и сохранность глифа в Windows
пока не подтверждены.

В обычной Debug-сборке диагностического IAT-зонда нет. По необходимости
`GLASS_DELPHI_DRAW_PROBE` можно вручную определить в Preprocessor Definitions
проекта GlassCore для отдельной x64 Debug сборки; сейчас он включается при
BeginPaint/GetDC exact TBitBtn и TToggleSwitch. Зонд не нейтрален и способен мешать штатным
IAT-перехватам: результат такой сборки нельзя использовать для визуальной
проверки; DLL/BPL, динамические API и операции вне сессии он не покрывает.

В предыдущем эксперименте TToggleSwitch был временно исключён по просьбе
пользователя; это решение впоследствии отменено, см. тест 15 ниже.

На Windows нужна обычная x64 Debug сборка без `GLASS_DELPHI_DRAW_PROBE`.
Проверить TBitBtn с глифом и без, текст, фон, hover/нажатие, disabled, фокус,
переключение вкладок и отключение/включение Glass; сравнить с обычной кнопкой и
предыдущими контролами. При дефекте прислать лог с записями DelphiBitBtn и
скриншот. Проверки исходного кода не заменяют сборку и визуальный тест.

## Тест 15: фон TBitBtn и возвращение TToggleSwitch

Пользователь подтвердил: текст TBitBtn уже рисуется на стекле, фон — нет.
В эксперименте теста 14 IAT `DrawThemeBackground` на `g_entryPointModule`
**уже был включён** наряду с `DrawThemeTextEx` на время `WM_DRAWITEM`;
без лога невозможно установить, нашёлся ли слот или какой именно guard
пропустил вызов. Ранее требовалось полное равенство `pRect` и `rcItem`.
Теперь разрешено их пересечение при неизменных проверках exact HDC, темы
Button и BP_PUSHBUTTON; сохранённый DC дополнительно клипируется по rcItem
и `pClipRect`. Это эксперимент, а не подтверждение причины. Обычный DEBUG
логирует `DrawItem begin` (theme/text/parent — полученные ссылки на IAT),
а при входе в DTB — HDC, theme, part, state, rect и rcItem, включая
несовпадения. Новый диагностический IAT ради этого не включается.

Решение исключать TToggleSwitch отменено: убраны запреты классификации и
прямого Root_Attach; exact класс снова попадает в общий Full/backdrop
Unknown → Root_Attach, как до исключения. Пользователь уточнил, что это
штатный VCL-компонент с собственным HWND; при системной теме Windows его
буферный Paint использует StretchBlt для фона родителя, Rectangle для
дорожки, FillRect для бегунка, DrawTextW для подписи, DrawFocusRect при
фокусе и финальный BitBlt. В другой конфигурации VCL styles могут рисовать
через тему. Это описание пользователя; отдельные вызовы и фактическая
принадлежность memory DC в `LogViewr-14` не записаны. В этом логе видны
несколько вложенных memory DC, в том числе созданных без source DC, и
клипы на момент создания ещё 1×1.

**Отдельная обработка бегунка пока не реализована**: общий Root может
чернить `WM_ERASEBKGND`, но последующий StretchBlt способен снова принести
фон родителя. Нельзя безопасно подменять первую попавшуюся FillRect или
произвольный memory DC на основе только времени/размера: во время paint
могут рисоваться родитель и другие вложенные буферы. Нет доказательства,
что alpha pattern brush сохраняет альфу через конкретные буферы VCL и их
финальный BitBlt. Нужны соответствие DC по операциям, выбранный bitmap и
границы прямоугольников; до этого визуальное исправление не заявляется.

В обычный DEBUG возвращён пассивный `VclEditProbe` для TToggleSwitch.
Для отдельного диагностического прогона по запросу добавлены в прежний
необязательный `GLASS_DELPHI_DRAW_PROBE` записи StretchBlt и DrawFocusRect,
сведения о bitmap приёмника и выбранном пере; в StretchBlt `a,b,c,d` —
source x/y/width/height. Он перехватывает IAT только EXE и только в
BeginPaint/GetDC точных TBitBtn/TToggleSwitch, ограничивает число сообщений
и не выводит текст. Внешние IAT-перехваты и штатные detours могут быть
нарушены порядком цепочки, поэтому зонд выключен по умолчанию и не годится
для визуальной проверки. Пустой журнал не означает отсутствие вызовов из
другого модуля, через динамические указатели или вне диапазона сессии.

Сначала собрать обычный x64 Debug без макроса и проверить TBitBtn; при
неудаче нужен лог `DelphiBitBtn` от запуска, включая begin/DTB entry. Для
выяснения буферного пути TToggleSwitch нужен отдельный диагностический
прогон: определить макрос в GlassCore, пересобрать, открыть страницу со
switch и выполнить по одному переключению и фокусу, затем прислать записи
`DelphiDrawProbe` и `VclEditProbe`; после этого убрать макрос и вернуться к
обычной сборке. Сборка и визуальная проверка Windows в Arena недоступны.

## Тест 21: изоляция удаления вложенного DC

В обычный `_DEBUG` добавлена ограниченная трассировка `DelphiToggleDC` поверх
уже существующего `PaintDispatcher::HookDeleteDC` — без новых detours/IAT и

не меняется; `LastError` после оригинала сохраняется через журналирование.

`DelphiToggleDC` со штатным `VclEditProbe` и API Monitor нужно выполнять в
одном процессе/прогоне по HDC и времени; HDC могут повторно использоваться,

прогона без платформы нельзя приписать проблему GlassCore.

Далее — собрать обычный Debug x64 и сопоставить полный лог с API Monitor для
одного запуска. Если выбранный инструмент не записывает стек последующего
ошибочного обращения, для него необходим capture stack в API Monitor либо
отладчик. После установления причин жизненного цикла сделать отдельное узкое
исправление и проверить оба состояния, фокус, клавиатуру, анимацию и соседние
элементы. Альфа-рендеринг TToggleSwitch и фон TBitBtn в этой версии ещё не
исправлены. Прогон в Windows и сборка здесь не выполнялись.

вызывается один раз. Остальные вызовы, стили кистей/пера и ошибки выделения —
оригинал. Глифы, текст, копирование буфера, анимация и обработчики ввода не
подменяются. Блокированные и вложенные сессии не освобождают внешние хуки.

владения memory DC: вложенная отрисовка родителя может использовать тот же
буфер. Поэтому проверки ограничивают область вмешательства, но не дают строгой
изоляции для произвольного приложения. При изменённых размерах bitmap, другом
типе пера, VCL style или анимационных кадрах с одним только копированием
обработчик намеренно может не сработать. Проверку визуального результата,
альфа-канала и совместимости с full debug detours необходимо выполнить на
Windows. Бюджетированный Debug лог: `[DelphiToggle] begin ... rectangle=... fill=...`,
`rectangle probe` с размерами и origin, `track` и `thumb` при успешной подмене.
Без этих `track`/`thumb` факт попадания в альфа-путь не установлен.

Проверить On/Off, hover, нажатие, клавиатуру, focus и анимацию, разные DPI и

Windows-сборка и проверка полей с фокусом/текстом, пустых и прокрученных списков,

## Тест 38: VCL ComboBox и альфа DTB

`TColorBox`, `TDriveComboBox`, `TFilterComboBox` отсутствовали в
`WindowClassifier`: теперь они направляются в тот же `ComboBox_Attach` и
GlassControlKind, что и `TComboBox`. Для настоящего дочернего `Edit` этих
классов действует существующая политика `WM_CTLCOLOREDIT`: только Full и
разрешённый backdrop, только системная сплошная кисть и системный цвет DC;
нестандартные цвета не заменяются. Нативные и WinForms ComboBox этим VCL-путём
не затронуты. Само подключение не гарантирует исправления текста и swatch,
которые VCL рисует через owner-draw: там пока не меняется отрисовка приложения.

геометрию и состояние без пользовательского текста; она пассивна.

настроенная константная альфа, а `CP_DROPDOWNBUTTON`,

адресной строки; вызовы вне сессии остаются оригинальными. У общей функции

область, для 255 вызывает оригинал, промежуточные значения используют DIB и
constant alpha; это не per-pixel alpha темы.

обычный Win32 и WinForms ComboBox, активное/неактивное окно и значения альфы

способ перехвата, а не повторное расширение гейта.

## Тест 41: только поле combo, непрозрачные заливки, текст VCL

Снимки после `f60def5` показали артефакты именно в поле, а не в выпадающем
списке: у `TColorBox` цветной образец стал полупрозрачным (сквозь него видна
подложка), выделенный текст получил смещённый светлый «призрак» и белую полосу,

оказался на светлом фоне. Причина в том, что снятая белая заливка была основой
для этих элементов: заливки образца и выделения сами по себе не непрозрачны, а

Теперь сессия `ODT_COMBOBOX` открывается только для поля (`itemID == -1` или
`ODS_COMBOBOXEDIT`) и подключает **только** `FillRect`. Строки выпадающего
списка идут прежним путём `ComboLBox`, текст, `DrawText` и `Rectangle` остаются
за VCL — `current->combo` в обработчиках текста гарантирует passthrough, даже
если слот включён другой сессией. Это возвращает штатную отрисовку текста и
убирает «призрак».

Правило заливок поля:
- системная кисть (`COLOR_WINDOW`/`COLOR_BTNFACE`) и прямоугольник, покрывающий
  не менее половины площади поля (в журнале это `[3,3,180,19]` при клиенте
  `[0,0,200,22]`), — это фон пустого значения; он заменяется на прозрачный
  чёрный (`PatBlt BLACKNESS`);
- любая другая сплошная кисть (образец цвета, полоса выделения, вставной фон)
  рисуется тем же цветом, но полностью непрозрачной кистью
  (`CreateSolidColorBrushWithAlpha(color, 255)`), иначе после снятия белой
  подложки она становится прозрачной;
- несплошные кисти, штриховки и всё вне границ поля — passthrough.

Debug `DelphiComboDraw fill` показывает `branch=system-background` для фона
поля и `branch=opaque-brush` для образца/выделения. Для `TColorBox` проверить
пустое значение, выбранный цвет и выделенный текст; для `TDriveComboBox` —
выбранный диск, длинный путь и выделение; для `TFilterComboBox` — регрессию.
Сборка и визуальный результат на Windows не проверены.

## Тест 49: фон VCL-таблиц без alpha-кистей; TInplaceEdit — Edit

Журнал 12 подтвердил, что `TStringGrid` (`0x7C0450`) и `TDrawGrid`
(`0x630E3C`) идут через `[GlassCore][DelphiGrid]`: `SetBkColor: entryPoint
COLOR_WINDOW→0`, `WhiteFill` ячеек, `Text` с `hr=0x0`. Правки по фактам:

1. **Фон таблиц — только `COLOR_WINDOW → 0`.** В `Root_MyCreateSolidBrush`, если

2. **Вводимый текст.** In-place редактор ячейки — окно класса `TInplaceEdit`
   (`hwnd=0xDA0F26`): в журнале для него только
   `SetBkColor … COLOR_WINDOW→0`, ни одной сессии `[Edit] BeginPaint`, потому что
   класса не было в классификаторе. `TInplaceEdit` добавлен в ветку `Edit`
   (`Edit_Attach` + `EditHooks`), как `TEdit`/`TMemo`.
3. **Заголовок `TStringGrid`.** Строк `DelphiGrid Fill` для `rect.top == 0` в
   журнале нет, поэтому фон заголовка не гасится. Чтобы не гадать, `DelphiGrid
   Fill` теперь логирует **каждую** заливку на DC таблицы:
   `Fill hwnd=… rect=[…] color=0x… style=… brush=…`, а `Text` — свой `rect`.
   По следующему журналу будет видно, чем именно закрашивается строка заголовка
   (цвет/`style`), и правка будет точечной.

Сборка и визуальный результат на Windows не проверены.

## Тест 50: фиксированные строка/колонка и `COLOR_BTNFACE` в таблицах

Скриншот после теста 49: текст ячеек виден (в т.ч. in-place `TInplaceEdit`), но у
`TStringGrid` остались белыми фиксированная верхняя строка и левая колонка, а у
`TDrawGrid` — часть ячеек. Это тест 49 и создал: для таблиц `COLOR_BTNFACE`
отдавался как есть (без alpha), а VCL заливает фиксированные ячейки
`FixedColor = clBtnFace`.

Решение: для классов `TStringGrid`/`TDrawGrid`/`TShownValueList` гасятся **оба**
системных «оконных» цвета — `COLOR_WINDOW` (обычные ячейки) и `COLOR_BTNFACE`
(фиксированные строка/колонка, часть ячеек `TDrawGrid`), и в
`Root_MyCreateSolidBrush`, и в `[DelphiGrid] Fill` (`systemFill`). Любой другой
цвет по-прежнему уходит обычной кистью, alpha-кисти для фона таблиц не
создаются. `WhiteFill` теперь логирует и `color=`, так что видно, какой именно
системный цвет погашен.

Сборка и визуальный результат на Windows не проверены.

## Тест 51: цветные ячейки таблиц — низкая альфа

Предложение пользователя (вместо теста 50, где `COLOR_BTNFACE` гасился в 0):
ячейки, цвет которых отличается от `COLOR_WINDOW`, должны одновременно
отличаться от общего фона и просвечивать сквозь стекло — то есть рисоваться
альфа-смешиванием с низкой альфой.

Как сделано для `TStringGrid`/`TDrawGrid`/`TShownValueList`:

- `COLOR_WINDOW` (обычные ячейки, фон) → сплошная чёрная кисть, то есть
  прозрачный фон (как раньше);
- любой другой цвет (фиксированные строка/колонка `TStringGrid` = `clBtnFace`,
  цветные ячейки `TDrawGrid`) → альфа `kDelphiGridCellAlpha` (тот же порядок,
  что у темы/комбо);
- то же правило в `Root_MyGetSysColorBrush` для `COLOR_WINDOW`/`COLOR_BTNFACE`,
  чтобы стоковые кисти не выпадали из политики;
- `[DelphiGrid] Fill` гасит в `BLACKNESS` только `COLOR_WINDOW`; alpha-кисть
  проходит в `orig()` и даёт полупрозрачную заливку.

Сборка и визуальный результат на Windows не проверены. Альфа настраивается
одной константой `kDelphiGridCellAlpha` в `RootGdiHooks.cpp`.

## Тест 52: чёрная очистка + AlphaBlend для цветных ячеек

Скриншот «и это при альфе 12?» показал, что цветные ячейки остаются плотными:
`FillRect` с pattern-кистью (`CreateSolidColorBrushWithAlpha`) **не переносит
альфу** — GDI пишет RGB и делает пиксель непрозрачным. Поэтому alpha-кисти для
фона таблиц больше не создаются (`Root_MyCreateSolidBrush` /
`Root_MyGetSysColorBrush` отдают обычную/системную кисть, `COLOR_WINDOW` → 0).

Новый порядок в `Root_MyDelphiGridFill` для сплошной кисти:

1. прямоугольник очищается `PatBlt(BLACKNESS)` — прозрачный фон;
2. если цвет отличается от `COLOR_WINDOW` — поверх кладётся цветная подложка
   через `FillRectWithAlphaBlend` (1×1 premultiplied DIB + `GdiAlphaBlend` с
   `AC_SRC_ALPHA`), альфа `kDelphiGridCellAlpha` (сейчас 100).

Так цвет ячейки одновременно отличается от общего фона и просвечивает, а не
смешивается со старым содержимым (что и давало «плотный» цвет). Стоковые кисти
`GetSysColorBrush(COLOR_WINDOW/COLOR_BTNFACE)` распознаются по хэндлу, потому что
`GetObject` для них не работает. В журнале: `WhiteFill` (только очистка) или
`AlphaFill … color=0x… alpha=100`.

Сборка и визуальный результат на Windows не проверены.

## Тест 53: текст с ETO_OPAQUE больше не стирает цветную подложку

После теста 52 цветные ячейки оставались невидимыми. Причина — порядок вызовов
VCL: в журнале 12 `WhiteFill`/`Fill` ячейки идёт **до** `Text`, а текст приходит
с `options=0x6` (`ETO_OPAQUE|ETO_CLIPPED`). Старая ветка `ETO_OPAQUE` делала
`PatBlt(BLACKNESS)` по прямоугольнику и стирала только что нарисованную подложку.

Теперь обе ветки используют одну функцию `ApplyDelphiGridCellBackground`:
1. `PatBlt(BLACKNESS)` — прозрачный фон;
2. если цвет (кисти или текущий `BkColor` для `ETO_OPAQUE`) не `COLOR_WINDOW` —
   `FillRectWithAlphaBlend` с `kDelphiGridCellAlpha` (100).

`ETO_OPAQUE` снимается перед `ExtTextOutWithAlpha`, поэтому текст ложится поверх
подложки, а не поверх чёрного. Проверка: цветные ячейки `TDrawGrid` и
фиксированные строка/колонка `TStringGrid` должны быть видны как лёгкая
подложка. Сборка и визуальный результат на Windows не проверены.

## Тест 54: TStringGrid — фиксированные ячейки и буферный DC

После теста 53 `TDrawGrid` показывает цветные ячейки, а у `TStringGrid`
фиксированные строка/колонка (`FixedColor = clBtnFace`) остаются почти
непрозрачными. Два возможных пути, оба закрыты:

1. VCL рисует таблицу в промежуточный bitmap (двойная буферизация) — тогда
   `WindowFromDC(dc) == NULL` и прежняя проверка `IsDelphiGridPaintDC`
   отбрасывала такой DC. Теперь владельцем считается окно активной paint-сессии
   (`GetPaintSessionHostHwnd`), если его класс — таблица; оконный DC
   по-прежнему обязан принадлежать именно ей.
2. Если заливка идёт в оконный DC — работает общий путь
   `ApplyDelphiGridCellBackground` (чёрная очистка + тинт с
   `kDelphiGridCellAlpha`).

В логи `Fill`/`WhiteFill`/`AlphaFill` добавлен `dcWnd=`, чтобы по журналу было
видно, в какой DC идёт заливка (NULL = промежуточный bitmap).

Сборка и визуальный результат на Windows не проверены.

## Тест 55: фон TStringGrid стирается до paint-сессии

Журнал для `TStringGrid hwnd=0x250C18` показал: для фиксированных ячеек
(`rect=[1,1,63,23]` — заголовок, `[1,26,63,48]` — левая колонка) **нет ни одной
строки `Fill`** — только `Text options=0x4` (без `ETO_OPAQUE`). Заливки есть
только у обычных ячеек (`WhiteFill … rect=[65,25,129,49] color=0x00FFFFFF`).
Значит фон фиксированных ячеек рисуется не в `WM_PAINT`, а при стирании окна —
до того, как `PaintDispatcher` положит окно в стек (`GetPaintSessionHostHwnd()`
ещё не указывает на таблицу), поэтому прежняя проверка `IsDelphiGridPaintDC`
отбрасывала такие вызовы.

Добавлено:
- `IsDelphiGridFillDC`: помимо активной сессии принимает DC, чьё окно — таблица
  (`TStringGrid`/`TDrawGrid`/`TShownValueList`) и нет чужого барьера. По классу
  окна — узко, другие окна не затрагиваются;
- тот же путь подключён к `PatBlt` (`PATCOPY`/`WHITENESS`) — стирание фона VCL
  делает им; слот `OHK_PATBLT` включается для таблиц вместе с grid-слотами;
- заливка стирания проходит через `ApplyDelphiGridCellBackground`
  (`COLOR_WINDOW` → прозрачность, прочие цвета → тинт с `kDelphiGridCellAlpha`).

Сборка и визуальный результат на Windows не проверены.
